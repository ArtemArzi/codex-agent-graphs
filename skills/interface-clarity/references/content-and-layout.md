# Content decisions in their visual context

Start with the audience's task and confirmed product behaviour. The same surface
may help someone choose, operate or read; its message order follows that job.
There is no universal landing-page section sequence, mandatory FAQ or hero size.

## Questions and information order

For the selected scope, map the questions that change a decision. A new visitor
may need to recognise what is offered, for whom/where, relevant conditions and
the next step. A returning user may only need their current state and an action.
Use actual customer language/questions when available. Do not turn every imagined
objection into a long section or delete important conditions to shorten copy.

Place an answer where the question arises. Show price scope, eligibility, timing,
commitment and consequences before the action they change, rather than relying
on remote fine print. Keep necessary terms intact and obtain the factual owner's
answer for unknowns. Supporting detail can be disclosed progressively when that
does not hide a material condition. Long useful content is not inherently bad.

For a broader structure task a compact map can be:

| Visitor question | Confirmed answer/source | Screen/state and prominence | Next action/consequence | How to check |
| --- | --- | --- | --- | --- |
| What happens after I send this? | Actual workflow says request, then availability confirmation | Beside request action, before submission | Send request; no reserved slot yet | Inspect next state; ask a participant to describe the consequence |

This is a method example, not a fact or wording to transplant to every booking
site. The product may actually confirm a slot immediately.

## Write by function

- Headings name the actual topic, value or state, so the section outline helps
  find an answer. Avoid empty slogans where the person needs to recognise the
  service. Preserve a deliberate expressive heading when context supplies meaning.
- Body copy explains the needed facts and conditions with familiar terms. Explain
  necessary specialist language; keep names consistent. Remove empty repetition
  without replacing precise meaning with vague brevity. Use tables/lists where
  they simplify a real comparison or sequence.
- Action text describes what the control does and, when needed, its object or
  consequence. Match the actual flow: requesting contact, selecting time, paying
  and confirming are different. A generic Continue can be clear in a known step;
  it is not automatically wrong everywhere.
- Forms use persistent labels, helpful examples and nearby format guidance.
  Placeholders do not replace labels. State what happens on submission and why
  unexpected information is needed. Keep error/recovery text near the affected
  control and preserve input where the product supports it.
- Loading, empty, error and success messages identify the actual state and useful
  next step. Do not claim acceptance, reservation or delivery from a button click
  alone, or invent a failure cause. Product behaviour must substantiate the words.

Keep the brand's voice where it helps understanding. Do not mimic the source
author's persona or impose English reading-age formulas on Russian copy.

## Make the important relationship visible

Inspect a real capture: competing emphasis, heading/body distinctions, visual
grouping, reading order, proximity of conditions to actions and decorative
elements that interrupt the task. Size, weight, space and contrast can express
relative importance. A three-font-size suggestion is not a mandatory rule.
Describe likely attention order as an expert hypothesis unless measured.

Distinguish a primary action from supporting actions where the task has a clear
priority. Repeating the same useful CTA on a long page is different from several
competing commitments. Selection screens and workbenches may need multiple valid
actions. Do not apply a single-CTA-per-page ban or force every answer above the fold.

Graphics should support the task, evidence or orientation when relevant; decorative
identity is not inherently a defect. Check whether prominent imagery displaces
essential information on the actual mobile screen. Do not invent benefit claims,
fake before/after results or hide conditions to make the screen persuasive.

Check readable wrapping, heading/label semantics, keyboard names, meaningful link
text, zoom/reflow and supported text-spacing overrides for affected UI. Use real
computed colours/tools for contrast values, not a visual guess. WCAG 2.2 AA text
contrast generally requires 4.5:1, or 3:1 for large text, with defined exceptions.
Text Spacing 1.4.12 tests tolerance to user overrides; it does not prescribe the
default line-height or letter spacing of every design. Targeted checks are not
proof of full WCAG conformance.

Validate changed copy in its real width and all materially affected states;
shorter strings can still wrap poorly or omit a necessary consequence. If layout
cannot be inspected, deliver the text/proposed arrangement and state that limit.
