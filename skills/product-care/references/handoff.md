Refer to actual available skills and project procedures. Skill names below are
conditional companions, not a mandatory chain or dependencies to install. If a
companion is absent, use an adequate native procedure within authorization and
report the narrower evidence; do not claim the absent workflow ran.

| Owner | Use when | Preserve |
| --- | --- | --- |
| Project Start | A real foundation/documentation contract gap needs creation or maintenance | Canonical docs owner; narrow changed-area maintenance rather than a new interview |
| Task Delivery | A concrete software task is chosen | Accepted question/decisions, exact affected scope, reproduction/evidence, intended behavior and quality checks; its task/handoff owns execution |
| Software Factory | Independent substantial parts and isolation benefit justify it, or user requests it | Optional delivery under TD; root owns integration, shared resources and acceptance |

## Project Start's linked disciplines

Project Start explicitly names Matt Pocock disciplines as companions within the
same work. Select the currently available local versions only for a real gap:

| Companion | Select when | Keep the current boundary |
| --- | --- | --- |
| `domain-modeling` | A business term or domain relationship is genuinely being changed or resolved | Read the mapped glossary/context and code first; ordinary consumption of an existing definition does not need this workflow. Preserve canonical term/ADR owners |
| `codebase-design` | A chosen implementation needs module/interface or seam design | Design within the owning TD task; an operational observation does not trigger a general architecture pass |
| `grilling` | An unresolved behavior, business rule or ownership choice changes the next decision | Ask only the material gaps, reuse accepted answers and continue independent work; no new full intake |
| `writing-for-agents` | A chosen improvement changes agent instructions or document navigation | Keep precise conditional pointers and one rule owner; it does not select workflow, review roles or authority |
| `to-questionnaire` | A specific external knowledge owner holds needed facts | Draft a focused owning deliverable; drafting does not authorize sending it |
| `retro` | Repeated tool/environment/navigation failures justify a bounded retrospective | Diagnose and propose from observed evidence; an ordinary product incident does not require retro or authorize instruction/config changes |

The optional setup/spec/ticket helpers mentioned by Project Start are not assumed
installed. Check the actual catalog when such a capability is needed and retain
Project Start's native fallback. Use no mandatory companion chain or installer.

## Continue the same outcome

Pass only useful context: the working episode, observed signal and affected
version/window, relevant evidence and confidence, decisions already accepted,
expected behavior/outcome, applicable constraints/authorization, existing task ID,
and the next useful check. Link raw evidence in its authorized source rather than
copying private records into briefs or creating a second mutable journal.

An authorized full outcome continues in the same task through those owners. A
handoff is not a reason to stop, repeat intake or ask for authority already given.
For a read-only request, prepare the next task without performing its mutations.
For a genuinely missing permission/business decision, leave that dependent step
pending and explain the concrete consequence.

Reuse original valid checks/reviews under the owning policy. Changed subject,
environment, data, instrumentation or contract may invalidate affected evidence;
a skill switch alone does not. Actual-target proof remains fresh. Keep deferred
checks visible without changing released schemas, receipts or graph identities.

Keep engineering completion separate from observation/application/effect. An
existing technical task can remain complete with an unproven business hypothesis;
record the follow-up in its existing owner without falsifying either status.
If no record exists, a concise note in chat or an authorized task artifact is
sufficient; no universal lifecycle JSON or tracking database is required.

An incoming Deployment follow-up names the expected user outcome, observed
release/target, affected episode, permitted evidence source and next meaningful
trigger/window. Verify availability and authority before reading that source.
Unknown owner/window stays unknown; do not invent an assignment or universal
soak duration. A prepared note is not a scheduled or executed check. If a new
software task is selected within existing authority, TD can choose Factory from
dependencies; Product Care neither starts writers nor bypasses its review.

Inherit the active host's risk/review/model policy. Add no automatic agent waves
or whole acceptance pair per mode. If an old controller cannot represent the
required review, preserve its state and follow the owning degradation procedure;
do not relabel a reviewer verdict or clear pending obligations.
