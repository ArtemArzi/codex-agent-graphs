# Handover

Scale this map to the delivered process and existing documents. Do not create a
second status ledger or copy customer knowledge into the skills repository.

| Concern | Transfer and verify |
| --- | --- |
| Capability | Supported tasks, channels/languages, exclusions and verified version |
| Acceptance | Agreed scenarios, evidence, unresolved defects and accepting owner |
| Human operation | Who reviews, intervenes, handles denial/unknown result and receives handoff |
| Access and data | Customer-owned accounts, scoped roles, data sources and lifecycle rules; never embed secrets in handover examples |
| Limits | Workload, cost/time budget, allowed autonomy, rate limits and stop controls |
| Recovery | Operation lookup, duplicate prevention, incident runbook, restore and release rollback evidence |
| Monitoring | Meaningful task/effect signals, alert destination/owner, tested escalation and quality sampling |
| Maintenance | Prompt/model/tool/corpus versions, update triggers, regression checks, support scope and change owner |
| Adoption | Training through actual tasks, staff/user observations and friction |
| Effect | Baseline, measurement window, comparable workload, denominator and remaining uncertainty |

Demonstrate that the intended operator can complete an ordinary task and a
relevant exception with the provided guidance. A forwarded PDF or account login
alone is not evidence of operational handover. For observability, distinguish
emitting a log from the responsible person receiving and understanding a signal.

Runtime skills and knowledge also need maintenance ownership. Changes to model,
provider route, instructions, tools, memory/retrieval or source policy can affect
behavior and trigger scoped regression/E2E checks. Repeat only affected checks
unless a broader risk remains. Preserve failed evidence and the known release.

Use existing business transaction records for a sale/payment and product records
for acceptance/use. Do not infer either from the other. Any scheduled follow-up
requires the user's requested scheduling mechanism and scope.
