# Project Start

Подготовь проект в два уровня: сначала минимально зафиксируй предметную область, затем — только после явного одобрения — создай проверяемое основание репозитория. Автоматизируй работу внутри этапа, но никогда не пересекай рубеж бизнес-логики, основания, плана или публикации задач без проверяемого результата и решения пользователя.

Команды ниже требуют Python 3.10 или новее. На Unix используй `python3`, на Windows — `py -3`; не рассчитывай на исполняемый бит файла.

## Неподвижные правила

1. Сначала исследуй существующий репозиторий; не перезаписывай и не дублируй его соглашения.
2. Храни сквозную бизнес-логику в одном каноническом документе. `CONTEXT.md` используй только как словарь, ADR — только для труднообратимых решений с реальным выбором.
3. Найденные факты проверяй самостоятельно. Решения задавай пользователю по одному и давай рекомендуемый вариант.
4. До одобрения бизнес-логики не выбирай окончательный стек, не создавай промышленный код и не раскладывай весь будущий репозиторий. Разрешён только явно одноразовый прототип под проверяемый вопрос.
5. Перед любой записью показывай план изменений. Не перезаписывай существующий файл без отдельного согласия.
6. Не заявляй готовность без выполненных команд и сохранённых доказательств.
7. Исправление повторяемой ошибки превращай в тест, проверку, ограничение зависимости или краткое правило с владельцем.
8. Корневой файл инструкций держи картой, а не энциклопедией; подробности размещай в адресных документах. Если уже есть `CLAUDE.md` или `AGENTS.md`, обновляй существующий файл и не создавай конкурирующий.
9. При вызове вспомогательного навыка правила рубежей, записи, полномочий и стоимости из `project-start` имеют приоритет. Не разрешай вспомогательному навыку незаметно писать, создавать ветку, коммитить, публиковать или запускать агентов.

## Начало каждого запуска

1. Найди корень репозитория и прочитай применимые `AGENTS.md`, `CLAUDE.md`, `CONTEXT.md`, карту документации, спецификации и ADR.
2. Запусти из каталога этого навыка:

   ```bash
   python3 scripts/project_start.py dependencies
   python3 scripts/project_start.py inspect --root <repo>
   python3 scripts/project_start.py status --root <repo>
   ```

3. Используй структурированный результат: `status`, `summary`, `next_actions`, `artifacts`, `data`. При ошибке назови причину, безопасный повтор и условие остановки.
4. Определи текущий этап по состоянию и реальным артефактам, а не по истории разговора.
5. Если `status` сообщает о старой `schema_version: 1`, сначала покажи безопасный перенос состояния:

   ```bash
   python3 scripts/project_start.py migrate --root <repo> --note "<зачем обновляется состояние>"
   ```

   Применяй его с `--apply` только после проверки путей и подтверждения пользователя. Команда сохраняет резервную копию, сбрасывает старые одобрения и возвращает проект в `discovery`; она не удаляет проектные файлы.
6. Если состояния ещё нет, сначала покажи предварительный просмотр:

   ```bash
   python3 scripts/project_start.py bootstrap --root <repo> --stage discovery
   ```

   Применяй его с `--apply` только после подтверждения пользователя.

Подробный автомат состояний, результаты этапов и условия восстановления читай в [references/lifecycle.md](references/lifecycle.md).

## Этап 1: предметная область

Используй `grilling` вместе с `domain-modeling`. Если запись ещё не была согласована, временно держи новые термины и решения в показываемом пользователю черновике; требование `domain-modeling` записывать термин сразу не отменяет рубеж записи `project-start`. Если пользователь явно запустил `grill-with-docs`, продолжай по созданным им артефактам, не повторяй интервью.

Собери в каноническом `docs/project/PROJECT.md`:

- результат и болезненную проблему;
- участников и ответственность;
- сквозной поток, состояния и переходы;
- правила, инварианты, данные и владельцев данных;
- ошибки, пограничные случаи и ручные исключения;
- границы первой версии и исключённое;
- нефункциональные ограничения и критерии приёмки;
- нерешённые вопросы.

Веди `docs/project/DECISIONS.md` как реестр бизнес-фактов, предположений, решений и рисков. Он входит в дайджест одобрения бизнес-логики; после рубежа технические решения записывай в `FOUNDATION.md` и адресные ADR, а изменение бизнес-реестра делай только через явный `reopen discovery`. Для большого многосессионного тумана предложи пользователю явный запуск `wayfinder`; не запускай его незаметно.

Перед рубежом прочитай [references/artifact-contracts.md](references/artifact-contracts.md) и выполни проверку `validate --stage discovery`. Записывай одобрение только после прямого подтверждения пользователя:

```bash
python3 scripts/project_start.py approve --root <repo> --gate business --note "<что именно одобрено>" --apply
```

## Этап 2: основание репозитория

После одобрения бизнес-логики строго сохрани порядок: **исследование → выбор стека → правила кодовой базы → правила тестирования → готовое основание**.

1. Сначала покажи предварительный просмотр и создай только пустые договоры основания:

   ```bash
   python3 scripts/project_start.py bootstrap --root <repo> --stage foundation
   python3 scripts/project_start.py bootstrap --root <repo> --stage foundation --apply
   ```

2. Обязательно запусти адресное исследование вариантов стека через `research` по первичным источникам. Сравни минимум два жизнеспособных варианта, если стек не задан внешним ограничением; при внешнем ограничении исследуй поддерживаемые версии, инструменты качества и риски. Сохрани отчёт и машинно зафиксируй завершение исследования с его путём.
3. Только по результатам исследования выбери не «самый модный», а наиболее простой профиль, удовлетворяющий бизнес-логике. Зафиксируй версии, цену выхода, отвергнутые варианты и отдельный рубеж выбора стека.
4. Только после выбора стека используй `codebase-design`: спроектируй глубокие модули, узкие интерфейсы, реальные швы и разрешённые направления зависимостей. Выведи из выбранного стека конкретные правила кодовой базы и зафиксируй их подэтап.
5. Затем исследуй официальные средства тестирования и качества именно выбранного стека. Выбери проверки по рискам и публичным швам, опиши быстрый и полный рубежи и зафиксируй подэтап качества.
6. Заполни версионируемый `.project-start/foundation.json`, архитектуру, стековые правила кодовой базы, стратегию качества, проектный порядок агентов, полномочия и журнал доказательств.
7. Создай только применимые исходные каталоги и настройки. Не навязывай веб-, контейнерный, облачный или многосервисный шаблон проекту, которому они не нужны.
8. Сделай локальные команды установки, запуска, остановки, сброса, проверки типов, тестов, форматирования, полной проверки и дымового сценария исполняемыми или явно пометь неприменимость с причиной.
9. Закодируй критичные архитектурные границы в линтере или структурных тестах; сообщение проверки должно подсказывать исправление.
10. Обнови короткую карту команд и договоров в уже существующем `AGENTS.md` или `CLAUDE.md`; если нет ни одного, спроси, какой создать. Сначала покажи точный блок.
11. Когда бизнес-, архитектурные и тестовые решения уже готовы, при необходимости предложи явный запуск `setup-matt-pocock-skills`, а затем `to-spec`. Это публикация согласованного договора в трекер, а не новый источник истины. Никогда не запускай `to-spec` до исследования стека и правил тестирования.
12. Проведи независимый обзор, сохрани его по образцу `assets/templates/FOUNDATION-REVIEW.md` и только затем зафиксируй `foundation-ready`.

Каждый подэтап фиксируй только с существующим доказательством; команда сама считает и сохраняет его SHA-256:

```bash
python3 scripts/project_start.py record --root <repo> --event foundation-research --evidence <отчёт-исследования> --note "<результат>" --apply
python3 scripts/project_start.py record --root <repo> --event foundation-stack --evidence <решение-о-стеке> --note "<результат>" --apply
python3 scripts/project_start.py record --root <repo> --event foundation-codebase --evidence <правила-кода> --note "<результат>" --apply
python3 scripts/project_start.py record --root <repo> --event foundation-quality --evidence <доказательство-проверок> --note "<результат>" --apply
python3 scripts/project_start.py record --root <repo> --event foundation-ready --evidence <независимый-обзор> --note "<critical/high отсутствуют>" --apply
```

Для решений читай только нужные файлы:

- стек, профили, модули и размеры — [references/stack-and-architecture.md](references/stack-and-architecture.md);
- тесты и проверочные рубежи — [references/testing-and-quality.md](references/testing-and-quality.md);
- безопасность, надёжность и цепочка поставки по риску — [references/risk-applicability.md](references/risk-applicability.md);
- полномочия, делегация, наблюдаемость и восстановление — [references/agent-operations.md](references/agent-operations.md).

После фиксации независимого обзора выполни `validate --stage foundation`. Затем, и только после прямого подтверждения пользователя:

```bash
python3 scripts/project_start.py approve --root <repo> --gate foundation --note "<что именно одобрено>" --apply
```

## Этап 3: крупный план и задачи

После одобрения основания сначала создай и согласуй верхнеуровневый план:

```bash
python3 scripts/project_start.py bootstrap --root <repo> --stage planning
python3 scripts/project_start.py bootstrap --root <repo> --stage planning --apply
```

Заполни `docs/project/PLAN.md` из 5–10 крупных сквозных частей. Для каждой укажи поведение, доказательство готовности, зависимости, основные риски и исключённое. Не дроби их на файлы и внутренние слои.

Проверь `validate --stage planning` и запиши одобрение плана только после прямого подтверждения пользователя:

```bash
python3 scripts/project_start.py approve --root <repo> --gate plan --note "<что именно одобрено>" --apply
```

Одобрение плана ещё не открывает реализацию. После него предложи явный запуск `to-tickets`. Требуй сквозные, самостоятельно проверяемые задачи с блокирующими связями; не создавай отдельные горизонтальные задачи «база», «сервер», «интерфейс», если они не дают завершённого поведения. Запиши доказательство публикации задач в состояние `project-start`; только этот рубеж переводит проект в `execution`.

Сохрани одобрение, индекс ссылок и отдельное подтверждение трекера по образцам `assets/templates/TICKETS-APPROVAL.md`, `assets/templates/TICKETS.md` и `assets/templates/TICKETS-RECEIPT.md`. Начальные значения `PENDING` не являются доказательством. Для локального трекера ссылки должны вести к существующим файлам задач. Для внешнего непосредственно перед фиксацией публикации выполни один доступный только для чтения запрос через API/CLI, сохрани сырой ответ или выгрузку в подтверждении, сверь точную ссылку/ID и укажи локальный путь в поле `Receipt`. Если живую сверку выполнить нельзя, не заявляй внешнюю публикацию: используй подтверждаемый локальный трекер либо остановись с явным блокером.

```bash
python3 scripts/project_start.py record --root <repo> --event tickets-approved --evidence <одобренный-список> --note "<что одобрено>" --apply
python3 scripts/project_start.py record --root <repo> --event tickets-published --evidence <индекс-задач> --note "<куда опубликовано>" --apply
```

## Этап 4: итерационная реализация

После одобрения плана и публикации задач разреши реализацию. Работай по одной задаче открытого фронта:

1. загрузи только нужную спецификацию, доменный контекст, ADR и задачу;
2. проверь исходное состояние и составь небольшой план задачи;
3. реализуй узкий сквозной результат;
4. выполняй быстрые проверки во время работы и полную перед завершением;
5. проведи независимую проверку по риску изменения;
6. обнови доказательства, решения, тесты и только затронутую документацию;
7. преврати повторяемую коррекцию в исполняемую проверку;
8. закрой задачу и возьми следующую только с открытого фронта.

Полный порядок и восстановление после перерыва находятся в [references/lifecycle.md](references/lifecycle.md).

Если пользователь запросил только подготовку, остановись в состоянии `execution` и сообщи, что репозиторий готов к реализации; не отмечай цель завершённой. Заверши первую цель `project-start`, когда:

- канонические документы и манифесты прошли проверку;
- команды проверки реально выполнены и доказательства записаны;
- независимый проверяющий не оставил критических замечаний;
- задачи опубликованы, а согласованный результат реализован и принят;
- известные риски, долги и отложенные решения не скрыты.

Зафиксируй выполненную реализацию и явную пользовательскую приёмку как разные события, затем заверши цель. Доказательство реализации должно быть каноническим `VERIFICATION.md`, дополненным **после публикации задач** новой успешной строкой с областью `implementation`, `execution`, `release`, `реализация` или `выпуск`; старое доказательство основания не подходит.

```bash
python3 scripts/project_start.py record --root <repo> --event implementation-evidence --evidence <путь> --note "<что доказано>" --apply
python3 scripts/project_start.py record --root <repo> --event user-acceptance --evidence <путь> --note "<что принято>" --apply
python3 scripts/project_start.py complete --root <repo> --note "<что принято и что осталось>" --apply
```

Приёмку сохраняй по образцу `assets/templates/ACCEPTANCE.md`. Записывай её только после прямого подтверждения пользователя, а не по собственному выводу агента.

Если одобренный документ изменился или нужно пересмотреть предпосылку, не переодобряй рубеж из поздней фазы. Сначала покажи явный откат без удаления файлов:

```bash
python3 scripts/project_start.py reopen --root <repo> --stage discovery --note "<почему меняется бизнес>"
python3 scripts/project_start.py reopen --root <repo> --stage discovery --note "<почему меняется бизнес>" --apply
```

Для пересмотра технического основания или плана выбери соответственно `foundation` или `planning`. Команда сбрасывает только зависимые одобрения и записи; существующие файлы сохраняет.

## Ограничение стоимости

Работай локально для последовательных и связанных шагов. Делегируй только независимое исследование, одноразовый прототип или итоговую проверку:

- обычно 0–2 вспомогательных агента;
- глубина 1, без потомков;
- не более двух повторов одного сбоя;
- один прототип одновременно;
- исследователь возвращает первичные источники и один ограниченный результат;
- проверяющий получает сырые артефакты, а не ожидаемый ответ.

Если нужен `prototype`, помести его в явно одноразовую изолированную область или временный каталог. Не следуй его правилу о ветке/коммите без разрешения в `AUTHORITY.md`; не размещай прототип в промышленном дереве до выбора стека. Если нужен `wayfinder`, создание задач, веток и фоновых исследователей также подчиняется текущим полномочиям и лимиту агентов.

Сжимай контекст на границах этапов: состояние, принятые решения, открытые риски, доказательства и следующий допустимый шаг. Не пересказывай всю историю.

## Служебные ресурсы

- `scripts/project_start.py` — осмотр, зависимости, безопасное создание, состояние, одобрения и проверка.
- `scripts/test_project_start.py` — самопроверка сценариев в одноразовом каталоге.
- `assets/templates/` — копируемые заготовки документов; не загружай их все в контекст без необходимости.
- Файлы `references/` — подробные правила, загружаемые по текущему этапу.
