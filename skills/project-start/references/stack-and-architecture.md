## 1. Сначала ограничения

Извлеки из одобренной бизнес-логики:

- форму продукта: сайт, API, мобильное приложение, библиотека, CLI, внутренний инструмент, обработка данных/ML;
- критичные пользовательские пути и время отклика;
- данные, объём, согласованность, хранение и переносимость;
- интеграции, офлайн-режим и фоновые задачи;
- безопасность, приватность и регулирование;
- среду развёртывания, бюджет и компетенции команды;
- требования к локальной воспроизводимости и агентной наблюдаемости.

Не обсуждай конкретные технологии до этой выжимки.

## 2. Обязательное исследование стека

Запусти `research` с ограниченным вопросом и потребуй первичные источники: официальную документацию, спецификации, журнал выпусков, исходный код и официальные показатели поддержки.

Сравни как минимум два жизнеспособных варианта по одной таблице:

| Критерий | Что доказать |
|---|---|
| Соответствие бизнес-пути | поддерживает ли критичные сценарии без обходных схем |
| Простота | сколько служб, языков и инструментов необходимо |
| Зрелость | поддержка, стабильность интерфейсов, обновления |
| Тестируемость | доступны ли быстрые и реалистичные швы проверки |
| Наблюдаемость | может ли агент видеть ошибки, журналы, метрики и путь UI |
| Развёртывание | воспроизводимость, стоимость, откат |
| Безопасность | поддерживаемые версии и подходящие защитные средства |
| Понятность агенту | типы, схемы, диагностические команды, распространённость |
| Выход из решения | стоимость смены технологии и переносимость данных |

Для каждого утверждения зафиксируй дату и источник. Если стек задан внешним обязательным ограничением, исследуй хотя бы версии, инструменты качества и риски выбранного стека.

## 3. Профиль основания

Выбери один профиль и сохрани его с версией в `.project-start/foundation.json`:

- `web-single-service` — интерфейс и сервер в одном развёртываемом продукте;
- `api-service` — API без основного пользовательского интерфейса;
- `mobile-client` — мобильный клиент с явно описанным серверным контуром;
- `data-ml` — конвейер данных, исследование или модель;
- `internal-tool` — ограниченный внутренний продукт;
- `cli-library` — CLI или библиотека;
- `custom` — только с объяснением, почему базовые профили не подходят.

Профиль задаёт версии среды, менеджер зависимостей, команды, минимальные проверки и применимые риски. Не превращай профиль в универсальный шаблон со всеми возможными службами.

## 4. Архитектурная позиция по умолчанию

Начинай с модульного монолита. Выделяй независимую службу только при доказанной необходимости отдельного развёртывания, масштабирования, изоляции риска или владения другой командой.

Проектируй глубокие модули:

- маленький интерфейс скрывает существенное поведение;
- доменная логика не зависит от фреймворка и внешней инфраструктуры;
- адаптеры располагаются на реальных швах;
- данные имеют понятного владельца;
- зависимости направлены внутрь доменной модели или по явно заданному графу;
- сквозные функции входят через ограниченные интерфейсы, а не импортируются отовсюду.

Не создавай интерфейс «на всякий случай»: один адаптер обычно ещё не доказывает необходимость абстракции.

## 5. Исполняемые границы

Выбери несколько критичных правил, которые можно проверить автоматически:

- допустимые направления импортов;
- запрет прямого доступа к базе вне владельца данных;
- размещение внешних интеграций и секретов;
- использование структурированных журналов;
- проверка входных данных на внешней границе;
- отсутствие циклических зависимостей;
- запрет импорта внутренностей другого модуля.

Реализуй их средствами выбранного стека: линтером, анализатором зависимостей, архитектурным или структурным тестом. Сообщение ошибки должно объяснять правило и безопасное исправление.

## 6. Размер и связность файлов

Используй размер только как сигнал:

- до 400 строк — обычно без специального внимания;
- 400–800 — проверить связность, количество причин изменения и глубину интерфейса;
- свыше 800 — потребовать разделение или записанное исключение;
- созданный автоматически код, данные и некоторые таблицы тестов могут иметь исключение.

Не дроби глубокий связный модуль на десятки проходных файлов ради числа строк. Главные показатели: одна ответственность, локальность изменений, ясные зависимости и тестируемый интерфейс.

## 7. Локальный договор команд

Каждый профиль обязан описать команды:

- `install` — воспроизводимая установка;
- `run` — локальный запуск;
- `stop` — безопасная остановка;
- `seed` — тестовые данные;
- `reset` — возврат локальной среды в известное состояние;
- `format` — форматирование;
- `lint` — статические правила;
- `typecheck` — типы или схемы;
- `test_fast` — быстрый цикл;
- `test_full` — полный набор;
- `verify` — единый рубеж перед завершением;
- `smoke` — критичный сквозной путь.

Если команда неприменима, запиши `not-applicable: <причина>`, а не оставляй пустое значение. Для параллельных рабочих копий изолируй порты, базы, очереди, временные файлы и очистку.

## 8. Шаблоны и генераторы

Используй в таком порядке:

1. **Профиль** — выбирает договор и ограничения.
2. **Небольшая заготовка** — создаёт только стабильную основу профиля.
3. **Генератор** — применяется точечно при стабильном входном договоре и проверяемом результате.

Закрепляй версию генератора и проверяй воспроизводимость. Не используй генератор вместо архитектурного решения и не добавляй инфраструктуру, которую нельзя запустить и проверить локально.
