# Готовые решения и генерация

## Когда читать и какой результат нужен

Читай при выборе реализации новой возможности, зависимости, расширения framework
или генератора. Для обычной правки внутри принятой реализации используй её
контракт; повторное исследование всего рынка не нужно.
Результат: обоснованный выбор, используемый публичный интерфейс и проверенная
реализация в разрешённой задаче. Plan/read-only scope сохраняет предложение,
не объявляя его внедрением. Решение принадлежит существующим FOUNDATION/
ENGINEERING/PLAN; отдельный каталог решений или новый skill не требуется.

## Выбрать подходящую основу

1. Найди фактические native возможности проекта, уже принятые библиотеки и
   расширяемые места. Сначала рассмотри их: готовые документы/операции ERP,
   framework hooks, проверенный клиент или генератор могут закрывать задачу.
2. Сравни подходящие варианты: native extension, поддерживаемая библиотека,
   генерация повторяющейся части, собственная ограниченная реализация.
   Оцени нужное поведение, API/данные, точные версии, сопровождение, лицензию,
   ограничения и цену интеграции по первичным источникам. Для существенного
   архитектурного выбора сохраняется действующий договор альтернатив проекта.
3. Выбирай по пригодности. Готовая библиотека не всегда лучше небольшого
   собственного кода; отсутствие подходящего генератора не требует его создания.
   Не добавляй TypeSpec/OpenAPI или ORM поверх уже достаточного native источника
   только ради совпадения с примером видео. Действующие требования не меняются.
4. Расширяй через документированные public API/hooks/plugins. Сохрани границу
   обновляемой зависимости и собственной бизнес-логики. Fork/patch upstream
   требует обоснованного выбранного решения; не исправляй vendor/generated code
   незаметно. Adapter нужен для реального согласования контрактов, а не как
   пустая обёртка над каждой функцией.
5. В разрешённом implementation scope подключи выбранное решение, зафиксируй
   dependency/config и проверь полезный сценарий и существенный отказ. Сохрани
   работающие инструменты, runtime и права; исследование само не разрешает
   глобальную установку, внешний доступ или публикацию.

## Если повторяющееся генерируется

Укажи один авторитетный источник (native schema, TypeSpec/OpenAPI, protobuf
или иной договор проекта), владельца, генератор/версию, команду и outputs.
Агент меняет источник и свою логику; типовой код воспроизводит генератор.
Нужное расширение генератора оправдывается повторяемым реальным вариантом,
а не желанием генерировать всё. Данные проекта и секреты не входят в шаблоны.

Проверь актуальность outputs повторной генерацией, типами и контрактными тестами.
Для детерминированных outputs повтор без изменения inputs должен дать чистый
diff; случайные/timestamp части устраняются или имеют узкое объяснённое правило.
Generated файлы обычно не правят вручную: stale/hand-edited output должен
обнаруживаться проектной проверкой. Проверку ошибочного output выполняй
в изолированном fixture, сохраняя исходную спецификацию и валидный результат.
Генерация не доказывает бизнес-правила или отсутствие несовместимости API.

В ENGINEERING достаточно краткого «что переиспользуем → почему → где расширяем
→ как проверяем/регенерируем» со ссылкой на actual config. Task Delivery
реализует выбранное; Factory передаёт единый dependency/schema/output owner;
Deployment проверяет нужную свежесть exact candidate; Product Care возвращает
конкретный обнаруженный пробел текущему владельцу. Повторный выбор на каждом
этапе и отдельная цепочка агентов не требуются.

Основание: выпуск «Как контролировать код ИИ-агентов»,03:15-14:20;
[TypeSpec](https://github.com/microsoft/typespec),
[generated-code pattern](https://github.com/mokevnin/dev-quality-gates/blob/main/docs/patterns.md#generated-code-gate).
Сохранённый разбор видео можно открыть через карту знаний workspace, если нужен
контекст. Частная база и полная расшифровка не являются обязательной зависимостью.
