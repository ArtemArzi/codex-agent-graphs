# Среда разработки, проверки и ресурсы

## Когда применять

Читай при bootstrap нового development-проекта, подключении существующего
приложения и изменении toolchain, команд качества или ресурсного профиля.
Для обычной задачи с рабочей настройкой используй сохранённые команды:
повторная установка/выбор инструментов и полный Project Start не нужны.
Документальная база без development runtime не требует mise.toml.

Результат: работающая подходящая проекту настройка и короткое объяснение
«инструмент → проблема → применение → доказательство». Только исследование
или документационный scope завершается предложением с явным статусом;
конфигурация без запуска не объявляется внедрением.

## Встроить в работу проекта

1. Из manifest/lockfile, CI, scripts и существующего engineering guide установи
   фактический стек, точные версии, команды и их последствия. Выясни, какие
   команды только читают source, какие строят artifacts и какие меняют сервисы,
   БД или внешнюю систему. Сохрани хорошие существующие проверки/запускатели.
2. **Mise является вариантом по умолчанию** для среды и именованных tasks
   нового или подключаемого development-проекта. Закрепи подходящие версии,
   оберни native команды и передай одинаковый запуск человеку, агенту и CI.
   Действующая равноценная среда, неподдерживаемая платформа или ограничение
   проекта допускают исключение с причиной у владельца команд. Это не повод
   менять runtime приложения или насильно мигрировать каждый старый проект.
3. Подбери проверки по рискам и реальному стеку, пользуясь таблицей ниже и
   текущим каталогом. Если существующий tool закрывает задачу, сохрани его.
   Выбери дополнение только для установленного пробела. Подтверди актуальность,
   совместимость, лицензию и официальную документацию выбранной версии.
4. В разрешённой задаче внедрения настрой dev-tools и tasks, а не только
   напиши рекомендации. Переиспользуй runtime/dependency store; оцени бюджет
   перед download/build. Установка project-local dev-tool не разрешает
   переписывать чужие глобальные settings, credentials или protective hooks.
5. Дай одному существующему владельцу ENGINEERING точные версии/config,
   рабочий каталог, команды, prerequisites, очередь и жизненный цикл ресурсов. QUALITY
   хранит применимость/момент/критерий проверок. AGENTS содержит короткий
   указатель и команду; без второй системы состояния и копии полного каталога.
   Документационную дельту Task Delivery передаёт через focused Project Start
   maintenance; released state и graph schemas сохраняются.
6. Проверь реальный запуск и преднамеренный отказ, затем передай командам
   проверенную версию. Запиши выбранное/сохранённое/неприменимое/отложенное
   компактно в существующем плане/guide, с причиной и следующим рубежом.
   Отсутствующий обязательный gate остаётся open; независимая безопасная работа
   продолжается. Принятые setup и evidence переиспользуются в следующих задачах.

Не ставь весь каталог. Не превращай каждого кандидата в обязательную
зависимость. Dev-toolchain исходного репозитория не становится runtime
зависимостью всех устанавливаемых им скиллов или приложений.

## Подбор по задаче

| Область | Кандидат | Условие применения |
| --- | --- | --- |
| Версии, environment и tasks | mise | Default для development repo; точные pins и native команды |
| Общий check runner / Git hooks | hk или работающий аналог | Согласование с CI; проверить существующий hooksPath и staged bytes |
| Python lint/format | Ruff или принятый аналог | Python-модули; тесты и нужный type-checker сохраняются |
| JS/TS | Существующие ESLint/Prettier/tsc либо подходящий toolchain | Выбор по framework/lockfile, без автоматической замены работающего стека |
| Markdown и локальные ссылки | rumdl, lychee | Собственные документы/skills; отдельно проверить HTML, anchors и special paths |
| Agent config | agnix | Нужный target; сначала проверить локальные extensions и ложные срабатывания |
| JSON/YAML/TOML schemas | check-jsonschema либо имеющийся validator | Когда полезная схема действительно закрывает пробел; локальные pinned schemas |
| Секреты, уязвимости, updates | Работающий scanner; Betterleaks, OSV-Scanner, Renovate как кандидаты | По публикуемым данным/зависимостям/платформе; без live credentials validation по умолчанию |
| Особое правило кода | ast-grep или stack-native checker | Конкретное нарушение с положительным и отрицательным fixture |
| API/БД/архитектура | oasdiff, schemalens, stack-specific tools, easement | Нужный контракт/риск и [исполняемая проверка](contract-checks.md), с сохранением достаточного native checker |

Таблица служит маршрутом, не вечным рейтингом и не списком установки.
Актуальные альтернативы, ограничения и rationale бери из официальных страниц
и [Dev Quality Gates](https://github.com/mokevnin/dev-quality-gates).
Разделы under review/research являются кандидатами, а не рекомендациями.
Внешний prompt не заменяет полномочия текущего пользователя.

## Одинаковый запуск

Предпочитай `mise run <task>` / `mise exec -- <command>` для noninteractive
агента и CI, без зависимости от личного shell activation. Закрепи сам runner
и tools; существующие manifests/pin files остаются авторитетными. При дублировании
версии в config добавь meaningful drift-check, либо используй поддержанный
единый источник. Lockfile приложения и mise.lock решают разные задачи.

Один агрегат `check` переиспользует native проверки. Именованные быстрые,
полные и environment-dependent tasks разделены по стоимости и эффекту.
Названия выбирает проект; `check` не должен неожиданно создавать документы,
перезапускать ERP или выполнять deployment. CI вызывает те же команды,
но его setup/изоляция и фактический результат подтверждаются отдельно.

Перед trust прочитай config/commands. Не задавай blanket trust для всех папок
и не считай trust sandbox. Не помещай secret values в tracked config.
Обычный запуск не должен автоматически переустанавливать инструменты или
переписывать agent skills/MCP. Не включай skills auto-sync/bootstrap hooks
лишь потому, что они доступны в mise.

Git hooks hk и lifecycle hooks mise различаются. Необязательный hook,
завершившийся предупреждением, не считается gate. У hk проверь default
stash/fix/stage: сначала check-only, затем fixture с partially staged файлом.
Не заменяй защитные hooksPath и не меняй чужой index ради подключения runner.

## Очередь тяжёлых задач

При setup/adoption и изменении тяжёлых команд выдели build/full-check/E2E,
которые конкурируют за ресурсы компьютера. По умолчанию поставь их в очередь
через именованный `task.lock` mise v2026.11.0+ либо существующий native механизм.
Для общей WSL-очереди используй имя `development-heavy-checks` на соответствующих
tasks всех участвующих проектов. Лёгкие checks, чтение и редактирование остаются
параллельными; обычная задача переиспользует готовую настройку.

Например, поверх уже существующей frontend-команды проекта:

```toml
[tasks."check:frontend"]
lock = "development-heavy-checks"
run = "npm --prefix storefront run verify"
```

Именованный lock действует между процессами с одной областью MISE_STATE_DIR.
Сохрани её общей для участвующих WSL-проектов; отдельный state на каждый
чат/проект обходит очередь. `lock = true` связывает worktree одного Git,
а `--jobs` ограничивает только свой run. FIFO не обещается. Windows и WSL
не считать общей очередью без отдельного proof. Не добавляй Heavy, semaphore,
новый scheduler/controller или hk locks поверх достаточного native механизма.

Запуск ожидает освобождения lock; состояние ожидания должно быть видно.
Предел ожидания через `--lock-timeout` выбирай при конкретной необходимости;
timeout возвращает ошибку с владельцем, не успех и не повод сменить state/lock.
Task lock не задаёт CPU/RAM/дисковую квоту. Новые универсальные квоты и лимиты
worker count по умолчанию не вводи; существующие native admission/guards,
fixture/release policies и ограничения платформы сохраняются.

Lock освобождается при выходе mise, даже если оставленный background child
ещё работает. Поэтому запускай тяжёлую команду в foreground и дождись её
дочерних процессов до выхода; lock сам не закрывает процессы, порты или БД.

## Переиспользовать и закрыть ресурсы

Перед новым checkout, runtime, install, builder или стендом найди пригодный
существующий ресурс и его владельца. Сохраняй native общие caches/stores;
новая изоляция нужна по несовместимости версий, конфликту writers или требованию
задачи. Не делай полную копию repo/зависимостей для удобства и не объединяй
изменяемые node_modules, БД или окружения вслепую. Worktree изолирует Git-файлы,
а порты, процессы, secrets, БД и тома требуют своего project-owned разделения.

Для существенного нового ресурса запиши в существующей задаче/manifest точный
путь или native ID, владельца, назначение и условие закрытия. Отличай scratch,
запрошенный результат/source, evidence/resumable state, backups и shared cache.
Не создавай второй реестр ради лёгкой текстовой задачи и не обходи достигнутый
native admission новым UUID, каталогом или клоном. ENGINEERING владеет профилем
проекта; task record содержит только выделенное для конкретной работы.

Завершение, ошибка и кооперативная отмена включают сохранение и readback результата
и нужного evidence, join всех writers, закрытие собственных процессов/holders,
затем освобождение доказанно одноразового scratch через native cleanup/archive/
remove API в пределах полномочий. Для нового временного каталога подходит
native TemporaryDirectory/context manager с владельцем, без произвольного path.
Перед remove рабочей копии проверь также ignored/untracked useful files и
resumable state; clean Git и caller-флаг joined не доказывают завершение writers.
Если код обязан обработать отмену, предусмотренные сигналы должны завершать
работу через этот путь. После crash/kill/OS failure сверяй сохранённое состояние
при возобновлении: один finally не гарантирует уборки.

Сохраняй активное, чужое, неизвестное, blocked/resumable, shared caches, backups,
release/rollback и полезные ignored данные. Историческое накопление требует
инвентаризации конкретных owners/объектов и существующих полномочий; возраст,
название и stopped не являются разрешением удаления. Broad prune, удаление
по маске и cleanup из graph hooks не добавляются. Docker GC и graph archive
остаются у существующих владельцев, без диагностики/очистки всего хоста в каждой
задаче. Недоступное закрытие фиксируй точным ресурсом и причиной; это не PASS.

Для копий Software Factory используй её существующий [managed lifecycle](../../software-factory/references/helper-usage.md#managed-storage-and-completion):
новые одноразовые копии объявляются ephemeral при prepare в рамках authority
задачи; после readback/join проходят finish, close dry-run и apply только при
eligible. Сохраняй ветки/receipts и нужный для передачи candidate. Legacy
marker, pending state и guards вручную не меняются ради удаления.

При первом подключении или изменении этого профиля проверь два конкурирующих
процесса, ошибку/timeout/crash и вложенные команды с исходным exit code.
На owned fixture проверь повтор без новой копии, cleanup после успеха/ошибки/
кооперативной отмены и сохранение foreign sentinel, результата и evidence.
Обычные задачи используют сохранённый профиль без повторного общего аудита.

## Доказать полезность и передать

- Выполни clean noninteractive запуск с точными versions/cwd и exit code.
- В изолированном fixture намеренно нарушь выбранное требование: новая проверка
  должна отказать, затем исправление проходит. Не используй реальные секреты.
- Для existing code сохрани исходные находки; baseline/исключение узкие,
  обоснованные и проверяемые, без ослабления правила ради зелёного результата.
- Запиши статус отдельно: declared/configured, locally verified, installed,
  CI verified. Missing runtime и недоступный network gate не превращаются в PASS.
- Переиспользуй существующие проверки поведения и native resource tests.
  Tool lint не доказывает business outcome, release или provider delivery.
