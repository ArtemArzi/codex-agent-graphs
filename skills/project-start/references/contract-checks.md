# Проверяемые ограничения архитектуры, API и БД

## Когда читать

Читай при bootstrap/adoption технического проекта и создании/изменении
существенной модульной границы, API, схемы данных или соответствующего check.
При maintenance обновляй только затронутые контракты. У обычной текстовой
правки без такого влияния нет обязательного архитектурного/DB прогона.
Сначала используй принятые требования, ENGINEERING/QUALITY, config и тесты;
инструмент не определяет допустимое бизнес-поведение.

## Из правила сделать проверку

Свяжи существенное правило с actual checker/config/командой, моментом запуска,
проверяемым source/artifact/environment и критерием. Сохрани одного владельца
стандарта/команд и одного владельца качества; достаточно существующих разделов,
без обязательного нового реестра или machine-schema. Отличай review, planned,
configured, local proof и реальный required CI.

| Контракт | Что имеет смысл проверять | Подходящий механизм и предел |
| --- | --- | --- |
| Архитектура | Направления зависимостей, public границы, циклы и запрещённые вызовы | Существующий boundary checker либо stack-native import/type/architecture tool. AST не доказывает dynamic RPC, доступ через БД или runtime права |
| API | Формат/типы, обязательность полей и совместимость изменения с потребителями | Native schema/tests; для подходящего OpenAPI oasdiff, для protobuf Buf как кандидаты. Shape-diff не доказывает авторизацию, повторяемость или бизнес-смысл |
| БД | Соответствие моделей/constraints, nullable/unique/FK, миграции и совместимость кода/данных | Framework-native проверки, подходящий consistency adapter/schema/migration lint и нужная integration. Соответствие схем не доказывает финансовый/товарный инвариант |

Подбирай по конкретному стеку и источнику истины; не подключай все категории
или инструменты из таблицы. Сохрани достаточный существующий checker.
Для нового выбранного механизма в разрешённом adoption scope создай config,
подключи команду к проектному агрегату и проверь success/нарушение. Только
описанный запрет не является автоматически исполняемым ограничением.
Если адекватного tool нет, выполни доступную focused проверку/review и оставь
точный непокрытый риск; не называй это mechanical enforcement.

## Доказательство и безопасная применимость

- Для нового правила предъяви valid и намеренно нарушающий fixture: checker
  должен отказать на нарушении и пройти после исправления. Сохраняй original
  failed evidence и бизнес-требование, не подгоняй спецификацию под code.
- Сравнение API/данных связывается с известной принятой baseline и exact
  candidate, а не с уже перезаписанным «старым» контрактом. Разрешённое breaking
  change следует текущему owner/version/migration договору проекта.
- DB/runtime проверки требуют названной доступной среды и полномочий. Знание
  connection string не даёт права читать production, запускать migrate/reset
  или создавать бизнес-операции. Используй разрешённые isolated fixtures;
  unavailable среда остаётся open, native release gates сохраняются.
- При подключении в старый проект сохрани найденные нарушения. Применяй узкий
  baseline/no-worsening или объяснённое исключение по правилам проекта;
  blanket suppress, отключение check или снижение его строгости не заменяют fix.
- Положительный запуск и exit code привяжи к кандидату/config/окружению.
  Валидная запись PASS, наличие test или CI YAML не доказывают исполнения.
  Reuse принятого evidence идёт через владельца с проверкой актуальности.

## Передача по существующему циклу

Project Start создаёт/обновляет нужный стандарт и check mapping; Task Delivery
реализует затронутые правила и передаёт документационную дельту обратно через
focused maintenance. Factory проверяет combined candidate и единое владение
shared contracts; Deployment использует required проверки/совместимость и
сохраняет незакрытые release prerequisites. Product Care приносит конкретную
регрессию/дрейф владельцу, без установки всего каталога и повторного bootstrap.

Кандидаты и ограничения: [Dev Quality Gates](https://github.com/mokevnin/dev-quality-gates),
[adoption и negative proof](https://github.com/mokevnin/dev-quality-gates/blob/main/docs/adopt.md),
[выбор среды и tools](development-tooling.md).
Для значимого изменения архитектуры сохраняется принятый
[архитектурный договор](documentation-contract.md#архитектурный-договор).
