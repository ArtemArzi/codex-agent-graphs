# Тестирование и качество

## Исходная формула

Для каждого существенного риска выбери самый дешёвый механизм, который надёжно обнаружит его до пользователя. Не стремись включить каждый вид теста.

После выбора стека обязательно проверь по официальным источникам поддерживаемые для закреплённых версий средства типизации/схем, модульных и интеграционных тестов, структурного анализа, сквозных проверок и безопасности. Запиши причины выбора инструментов; не переноси названия библиотек из другого стека по аналогии.

## Базовый набор

Почти для любого рабочего проекта обеспечь:

1. воспроизводимую сборку или загрузку приложения;
2. типизацию либо проверку схем на внешних границах;
3. быстрые поведенческие тесты доменных правил;
4. интеграционные проверки реальных адаптеров, которыми проект владеет;
5. небольшой дымовой путь через собранный продукт;
6. проверку форматирования, зависимостей и случайных секретов;
7. единую команду `verify`.

## Матрица применимости

| Проверка | Добавлять, когда | Не делать обязательной, когда |
|---|---|---|
| Модульная/поведенческая | правила, расчёты, переходы, ошибки | проходной код без поведения |
| Интеграционная | база, очередь, файловая система, сеть, миграция | чистая библиотека без инфраструктуры |
| Договорная | независимые потребители/поставщики, публичный API, webhook | внутренние модули одного приложения |
| Сквозная | критичный путь сайта/приложения | каждая ветка доменной логики |
| Тест свойств | парсер, сериализация, расчёт, машина состояний, инварианты | обычный CRUD без ясного свойства |
| Миграция/откат | меняется долговечная схема или формат | нет долговечных данных |
| Мутационная | критичная детерминированная логика и уже зрелые тесты | каждый PR, UI и ранний прототип |
| Производительность | есть цель задержки/пропускной способности | нет пользовательской или эксплуатационной цели |
| Визуальная/доступность | есть пользовательский интерфейс | API, CLI или внутренняя библиотека |
| Оценка поведения AI | продукт содержит недетерминированную модель | обычная детерминированная программа |

## Выбор швов

До написания тестов перечисли публичные швы модулей и критичные пути. Тестируй наблюдаемое поведение через тот же интерфейс, которым пользуется вызывающая сторона.

- Не проверяй внутренний порядок вызовов без бизнес-причины.
- Мокай внешнюю границу, а не собственную доменную логику.
- Для базы и очереди предпочитай реалистичную локальную среду, если она остаётся быстрой и изолированной.
- Не допускай теста, который повторяет реализацию и не способен упасть при дефекте.
- В спецификации фиксируй ожидаемое поведение и шов, но не привязывайся к будущему имени тестового файла.

## Цикл во время реализации

1. Воспроизвести исходное поведение или записать падающую проверку.
2. Сделать минимальный сквозной результат.
3. Запускать `test_fast`, типы и затронутый структурный тест во время работы.
4. Перед завершением выполнить `verify` и дымовой путь.
5. Сохранить команду, результат и артефакт в `VERIFICATION.md`.

Не принимать «тесты должны пройти» как доказательство. Требовать фактический код возврата, краткий результат и путь к журналу/снимку/отчёту, если он нужен.

## Дефект превращается в актив

После дефекта или замечания обзора определить лучший долговечный носитель:

- регрессионный тест — повторяемое поведение;
- структурная проверка — архитектурная граница;
- тип/схема — форма данных;
- линтер — локально распознаваемый плохой образец;
- обновление словаря/ADR — недостающая модель или решение;
- задача уборки — накопившийся, но не блокирующий долг.

Не добавляй ещё один абзац в корневой файл инструкций, если правило можно выполнить машиной.

## Нестабильные проверки

- Не скрывай нестабильность бесконечными повторами.
- Зафиксируй владельца, воспроизводимость и срок исправления.
- Допускай ограниченный повтор только как временную диагностическую меру.
- Третья одинаковая ошибка означает остановку и разбор причины, а не ещё один запуск.

## Метрики полезности

Для первых итераций отслеживай:

- долю задач, прошедших проверку с первой попытки;
- число повторов и переделок;
- время до рабочего сквозного результата;
- стоимость принятой задачи;
- дефекты после приёмки;
- долю изменений, которые сохранились без отката/существенной переделки через 7 и 30 дней;
- замечания, превращённые в исполняемые проверки.

Не оптимизируй число тестов или строк покрытия без связи с риском.
