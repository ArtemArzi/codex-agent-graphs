# Договор артефактов

## Единственные источники истины

| Артефакт | Что хранит | Чего не хранит |
|---|---|---|
| `docs/project/PROJECT.md` | сквозную бизнес-логику, границы и критерии результата | стек, файловый план, историю реализации |
| `CONTEXT.md` | точные доменные термины и короткие определения | спецификацию, задачи, технические решения |
| `docs/adr/*.md` | труднообратимые решения с альтернативами и последствиями | каждое локальное решение |
| `docs/project/DECISIONS.md` | бизнес-факты, предположения, решения и риски, входящие в одобрение бизнес-логики | технические решения после бизнес-рубежа и подробный пересказ обсуждений |
| `.project-start/foundation.json` | машинно читаемый профиль основания и команды | объяснения и длинные обоснования |
| `docs/project/FOUNDATION.md` | обоснование стека, технические решения, архитектуру, эксплуатацию и документацию | бизнес-логику |
| `docs/project/CODEBASE.md` | правила языка, модулей, ошибок, зависимостей и файлов | бизнес-требования и список задач |
| `docs/project/QUALITY.md` | риски, швы, проверки и рубежи качества | полный список тестовых файлов |
| `docs/project/AUTHORITY.md` | разрешённые эффекты агента и необходимые одобрения | секреты и учётные данные |
| `docs/project/AGENT-OPERATIONS.md` | проектный порядок работы агентов, контекст и остановки | общую документацию Codex и длинные учебники |
| `docs/project/PLAN.md` | 5–10 крупных сквозных частей | мелкие задачи и реализационные подробности |
| настроенный трекер | небольшие задачи, блокировки и состояние исполнения | каноническую бизнес-логику |
| `docs/project/VERIFICATION.md` | фактически выполненные проверки и доказательства | намерения «проверить потом» |
| `.project-start/state.json` | текущий этап, последовательные подэтапы, дайджесты одобрений и пути к артефактам | содержимое самих документов |

Если два файла пытаются владеть одним фактом, выбери владельца и замени второе место ссылкой.

## Реестр решений

Для каждого значимого пункта записывай:

- идентификатор;
- вид: `fact`, `assumption`, `decision`, `risk`;
- формулировку;
- состояние: `open`, `validated`, `rejected`, `accepted`, `mitigated`;
- первичный источник или доказательство;
- владельца решения;
- способ проверки;
- срок/условие пересмотра;
- последствия ошибки.

Не пропускай предположения в спецификацию как подтверждённые требования. Непроверенное предположение должно стать экспериментом, задачей исследования или явным принятым риском.

## Короткий корневой файл инструкций

Сохраняй уже существующий корневой `AGENTS.md` или `CLAUDE.md` краткой картой. Не создавай второй конкурирующий файл; если нет ни одного, спроси пользователя, какой формат нужен:

1. цель репозитория;
2. основные команды;
3. архитектурные границы;
4. пути к бизнес-логике, словарю, ADR, качеству и плану;
5. опасные действия и условия одобрения;
6. правило обновления документации.

Не копируй в него содержимое адресных документов. Для крупных подпроектов разрешай более узкие вложенные инструкции, если область применения очевидна.

## Свежесть и проверяемость

- Добавляй владельца или условие пересмотра для быстро устаревающих документов.
- Проверяй относительные ссылки и существование обязательных файлов.
- Связывай каждое одобрение с дайджестами одобренных артефактов; изменение исходного документа требует явного пересмотра и сброса зависимых рубежей.
- Помечай созданные автоматически разделы и проверяй их регенерацию.
- Сверяй документацию с исполняемыми командами и кодом, а не только с другими документами.
- На каждой итерации обновляй только документы, смысл которых реально изменился.

## Правила записи

1. Перед созданием покажи пути и назначение файлов.
2. Существующий файл не перезаписывай: дополни совместимый раздел либо запроси решение.
3. Не создавай пустые каталоги «на будущее».
4. Не создавай новый документ, если достаточно добавить раздел в канонический.
5. Не записывай чувствительные данные, токены и реальные секреты.
