# Проектирование через использование

Читай при проектировании существенного публичного интерфейса, нового владельца
данных или изменении ответственности модулей. Это часть текущего Project Start,
а не отдельный архитектурный цикл. Начни с требований, принятой архитектуры и
реальных потребителей; применяй [архитектурный договор](documentation-contract.md#архитектурный-договор).

## Сначала сценарий потребителя

Для затронутой границы покажи несколько реалистичных примеров использования:
кто обращается, что передаёт, какой результат получает и какой эффект наблюдает.
Добавь существенный отказ или повтор, если они возможны. В старом проекте сначала
восстанови нынешние вызовы и совместимость; пример желаемого поведения помечай
предложением, пока соответствующее решение не принято.

Например, создание заявки может вернуть её ID и статус принятия, пока уведомление
ещё ожидает отправки. Это разные результаты. Из сценария должны быть видны
владелец сохранённого состояния, поведение повторного обращения и способ узнать
исход сбоя. Не добавляй очередь или отдельный сервис только ради примера.

Выведи из сценариев минимальный контракт:

- вход, результат и наблюдаемые эффекты;
- владелец данных и место проверки инварианта;
- ошибки, повтор, порядок действий и совместимость по применимости;
- что потребитель обязан знать и какую сложность модуль скрывает;
- наблюдение, отличающее правильный результат от неправильного.

Типы или псевдокод помогают уточнить контракт, но scaffold в рабочем коде не
нужен для завершения проектирования. Вызовы и описание интерфейса должны
согласовываться с требованиями, а не подгонять требования под удобную реализацию.

## Выбор в масштабе проекта

Для существенного нового решения сравни минимум два реалистичных подхода по
сценариям, цене изменения и эксплуатации, отказам и ограничениям команды.
Объясни рекомендуемый вариант и принятый компромисс. Используй доступный
codebase-design для глубины интерфейса; вариативность должна быть настоящей.

При подключении существующего проекта сохрани принятый стек и полезные документы.
Отличай известную причину выбора от неизвестной истории. Переиспользуй актуальное
исследование. Если native bootstrap требует недостающее сравнение стека, оцени
реальные варианты сохранения/изменения либо зафиксируй подлинное внешнее
ограничение с источником. Возраст проекта сам по себе не является external_constraint.
Не выдумывай альтернативы и не отмечай исследование completed до выполнения
действующих требований foundation manifest. Maintenance без нового выбора
не начинает это исследование заново.

## Результат и передача

Запиши сценарии и контракт в существующем владельце foundation/ADR, а точные
правила и команды — в engineering/quality. Не создавай отдельный rationale-файл,
если выбранный документ уже вмещает решение. В плане среза укажи точный раздел,
владельца интерфейса/данных, готовую предпосылку и критерий проверки.

Перед передачей следующей части сравни принятое решение, код и доказательства.
Согласованное изменение контракта обновляет owning документ через существующий
Project Start maintenance; пока он не обновлён, передай явную документальную
дельту. Несогласованное изменение остаётся открытым. Не переписывай требования
или тесты для оправдания кода; применяй development-recovery при настоящем
расхождении по его условиям.

Готовность: следующий исполнитель может восстановить допустимые вызовы,
результаты/ошибки, владельца состояния и нужную проверку по переданному разделу.
Запланированная реализация и непроверенный контракт остаются таковыми.
