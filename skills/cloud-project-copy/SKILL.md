# Копия проекта в Codex Cloud

Вызов: `$cloud-project-copy Подготовь копию этого проекта в Codex Cloud и проведи меня по шагам`.

Результат: рабочая копия проекта с нужными скиллами, контекстом, зависимостями и проверенными доступами. Агент выполняет технические шаги и просит человека только о недостающем выборе, разрешении или вводе секрета в защищённую форму. Запрос карты/инструкции ограничивает работу подготовкой; сам вызов навыка не разрешает публикацию, расширение прав или деплой.

## 1. Определить проект и продолжить существующее дело

Прочитай ближайшие AGENTS.md, карту документации и владельца текущей задачи. Найди фактический Git приложения, remote, branch и commit; рабочая база Work или компания могут владеть контекстом отдельно от кода. Не подменяй приложение текущим cwd. Сверь уже подготовленную Cloud environment, её владельца и предыдущий результат, если они известны. Вопрос о проекте нужен только при оставшейся неоднозначности.

Проверь tracked, untracked и нужные ignored файлы, локальные изменения и отличие от remote. Зафиксируй точный состав переносимой версии и судьбу незавершённых правок. Клон remote не включает несохранённые локальные bytes. Сохрани исходный проект и чужую работу; не делай автоматический commit/push всего дерева. Используй существующий путь изоляции и доставки проекта. Если разрешённой доставки этих правок ещё нет, закончи независимую подготовку и назови конкретный недостающий шаг.

Продолжай запись у существующего владельца задачи. Достаточно актуальных ссылок на исходную версию, выбранную среду, пакет, проверки и следующий шаг. Не создавай второй STATUS, граф или реестр подключения.

## 2. Переиспользовать доступы

Сначала проверь уже подключённые GitHub, Cloud environment и Composio доступными средствами. Подтверди GitHub чтением известного файла именно целевого репозитория. Каталог инструментов или карточка аккаунта этого не доказывают. Не проси заново подключать рабочие аккаунты и не создавай дубль среды.

При настройке внешних доступов прочитай [services.md](references/services.md). Различай чтение/запись через GitHub MCP и credentials для команд git. Права, ключи и сетевые настройки нужны конкретному хосту и операции. Отсутствие доступа через один канал не требует перевыпуска уже рабочего подключения через другой.

## 3. Подготовить Cloud и полный пакет

Сверь текущую [официальную документацию Cloud environments](https://learn.chatgpt.com/docs/environments/cloud-environments) через доступный официальный источник. Определи используемый интерфейс: современная prepared environment и legacy setup отличаются. Для современного пути выбери существующую подходящую среду или подготовь новую с нужным репозиторием. Если управление доступно только человеку, дай один конкретный шаг в интерфейсе и продолжай независимую подготовку. Отправка поручения в другой чат и создание чата требуют разрешения пользователя.

Найди актуальный доверенный private bundle и его manifest, либо подготовь сборку из canonical источников по [PORTABLE-KIT.ru.md](https://github.com/ArtemArzi/codex-agent-graphs/blob/main/docs/PORTABLE-KIT.ru.md). Обычный публичный клон CAG даёт поддерживаемое ядро, но не весь личный пакет с адаптированным ECC и выбранными знаниями. Число и состав берутся из manifest. Если полный архив недоступен в Cloud, явно оставь доставку пакета открытой; согласуй приватный канал, не публикуй архив/знания и не объявляй core полным пакетом.

Проверь bundle штатным `verify-bundle`, установи целиком штатным installer в новый или уже принадлежащий ему target и выполни `verify`/`doctor`. Не подменяй установку копированием отдельных SKILL.md и не перезаписывай активный глобальный CODEX_HOME. Обновление и rollback принадлежат тому же installer. Auth, sessions, browser profiles, локальные ключи и весь личный home в пакет не входят.

Определи, откуда именно Cloud-агент читает навыки, роли и инструкции. Файлы в VM, запуск вложенного CLI и переменная CODEX_HOME сами по себе не доказывают, что основной Cloud-агент их загрузил. Используй поддержанный данным хостом путь и native discovery; если он неизвестен или недоступен, отметь точный пробел, сохрани рабочие файлы и не объявляй совместимость подтверждённой. Не ослабляй host permissions ради переносимости.

## 4. Подготовить зависимости и необходимые сервисы

По lockfiles, runbook и `doctor` установи нужные проекту версии и зависимости. Не запускай установщики всех скиллов заранее. В Install script сохрани проверенные команды подготовки, в Start skill - запуск нужных сервисов и проверку готовности. Выбери разрешённый проектный контекст без секретов и клиентских БД; наличие private знания в пакете не разрешает его передачу любой команде. Для личного пакета проверь состав prepared filesystem и доступ к среде, по умолчанию Only me.

Для Composio или сервера выполни относящуюся ветку [services.md](references/services.md). Если сервис не нужен текущей работе, не делай его обязательным условием. Ключи человек вводит в поддержанную защищённую форму; агент записывает только имена требований и статус проверки. При ручном входе останови действия в этом окне до ответа человека. Никаких ключей в чате, Git, выводе команд или handoff.

## 5. Проверить и провести до новой задачи

В подготовленной среде выполни применимые проектные проверки, проверь фактический source commit и согласованные локальные дополнения. Проверь native обнаружение нужных скиллов, чтение их вложенного ресурса и необходимого контекста. Для нужных сервисов отдельно проверь реальное безопасное чтение в пределах действующих прав; один поиск схем не подтверждает работу сервиса. Сохрани ошибки и недостающие права без автоматического расширения.

Покажи коротко, что подготовлено, что проверено и что осталось. При наличии соответствующего разрешения проведи через Save/Publish (для обновления Edit/Republish), дождись подтверждения публикации и начни проверку в НОВОЙ задаче. Если действие выполняет человек, дай ему точный шаг; не создавай новый чат автоматически. Повтори в новой задаче только проверки переноса: версия исходников, native скиллы/ресурсы, запуск проекта и нужные подключения. Старый чат сохраняет собственное состояние и не подтверждает обновление среды.

## Завершение и возобновление

Подготовка завершена, когда сохранены пригодные для запуска настройки и проверенные файлы, а оставшиеся ручные действия названы точно. Перенос подтверждён только после проверки новой задачи из опубликованной среды. Различай эти состояния в отчёте. Отдельно сообщи про локальное сохранение, доставку в Git и фактическую доступность Cloud; не называй это выпуском приложения на сервер.

После перерыва перечитай владельца задачи, текущую версию исходников и состояние среды/подключений. Продолжай с первого неподтверждённого шага, сверяя неопределённый внешний результат перед повтором. Обновление репозитория не заменяет Republish изменённых install/start настроек. Обновление пакета не означает обновление уже открытых Cloud задач.
