# Product demonstration: choose what the evidence can support

Use only when showing the product or result helps the visitor decide. Choose:

- A real interactive sample when the available implementation can safely do the
  useful thing; explain its limits and preserve data/permission boundaries.
- A recording of an actual interface, using available ui-demo/project tools,
  when the demonstrated version and scenario are known.
- A clearly marked staged animation when explaining a concept, visual mechanism
  or approved design; it is not evidence that the simulated action exists.

A still can be the best answer. Do not add a capture pipeline, Figma token,
paid service, library, stock asset or remote call merely because a source uses it.
Resolve enabled capabilities and use existing authorized tools. Never assume a
credential or installed runtime from a foreign SKILL.md.

## When motion earns its place

Give each motion a specific explanatory job, preserve the accepted frame and
background, and verify a stable final still against the actual source. Different
story stages must remain understandable at the delivered size. Avoid automatic
loops on every chart, card, image, logo row or text section.

For a website, keep essential information readable before enhancement; use real
HTML text, purposeful user feedback, reduced-motion alternatives and offscreen
pause where relevant. Do not conceal the offer until scroll reveals complete.
For a showcase export, agree formats, dimensions, duration and size constraints;
MP4, GIF and a specific resolution are not universal deliverables.

Record generation/source provenance and licensing with shipped assets. Choose
formats and playback from the actual project's resource budget, and measure a
reported performance bottleneck before prescribing a remedy. A capture that looks
smooth does not establish field performance or the behavior of a real backend.

## An explicitly ambitious first screen

When the brief asks for an extraordinary live experience, a still plus large type
is not evidence that this request was met. Choose one visible authored mechanism
from the subject: a physical object responding to wind, a meaningful transition
or a direct manipulation. Explain the offer and keep the primary action usable
before the enhancement loads. Do not equate a library installation with visual craft.

Give the mechanism one lifecycle owner. Compose manual pause, reduced motion,
offscreen visibility, hidden documents and modal interruption; resuming one cause
must not override another. Entrance animations need this lifecycle too. Verify
actual changing frames, a stable readable still and module/render failure with
the same product flow. Desktop layering may need a simpler mobile composition.

The repository's `products/interface-design/demo-landing` is one original example:
a code-rendered cloth passes between two headline layers on desktop, while both
words stay above it on mobile. Its wind/pause controls and route planner are real;
the destination is explicitly fictional. Three.js is a local demo dependency,
not a mandatory dependency of this skill or a default for every landing.

Source basis: Elaya design-to-motion, retained as a pinned text reference in
[sources.lock.json](sources.lock.json). Selected ideas are fidelity, explicit
website/showcase scope, stable stills, reduced motion and offscreen pausing.
Its compulsory per-visual stories, visual presets and default export pipeline
are not active instructions here.
