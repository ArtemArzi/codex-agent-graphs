# Автомат задачи

## Источники состояния

Соблюдай иерархию в таком порядке:

1. системные, средовые и иные обязательные правила запуска;
2. применимые `AGENTS.md` и договоры явно используемых навыков;
3. прямой запрос пользователя и выданные им полномочия;
4. каноническая спецификация, задача трекера, проектные договоры, ADR и существующая система этапов (`project-start`, GSD или своя);
5. локальные доказательства конкретной задачи `task-delivery`;
6. история разговора и краткие пересказы.

`task-delivery` не создаёт новый жизненный цикл проекта. Если `project-start` ещё не открыл реализацию, верни управление туда. Если задача ведётся во внешнем трекере, сохрани в локальном плане ссылку и точный снимок требований, но не объявляй локальный файл главным.
Runtime проверяет это машинно: при наличии `.project-start/state.json` новая задача и её завершение допустимы только в Project Start `execution|complete` и при закрытом maintenance status.

## Режимы и состояния

```text
plan:
  planning -> awaiting_approval

implement:
  awaiting_approval -> implementation_intent -> implementing
  -> progress_checkpoint -> reviewing -> ready_to_complete -> completed

full:
  planning -> ready_to_implement -> implementing
  -> progress_checkpoint -> reviewing -> ready_to_complete -> completed
```

Обязательные доказательства идут в одном порядке:

```text
capabilities
-> internal-research + external-research
-> plan
-> plan-review
-> plan approval
-> progress checkpoint после каждой существенной части
-> verification
-> code-review
-> handoff
-> complete
-> project-start maintenance (если .project-start/state.json существует)
```

Повторная запись раннего доказательства сбрасывает зависимые поздние записи и одобрение. Изменение файла после фиксации делает его запись устаревшей. `status` сообщает расхождение SHA-256; он ничего не исправляет автоматически.

Проверенный `HANDOFF.md` является входной квитанцией для document-maintenance route, но не семантическим одобрением. `complete --apply` ставит durable pending marker до terminal task state, затем привязывает к Project Start обязательство `maintenance-required`; повторный `complete --apply` безопасно восстанавливает запись и снимает marker после успеха. Незакрытые `maintenance-required`, `running`, `blocked`, `reopen-required`, `restart-required`, pending marker и любой неизвестный maintenance status запрещают следующую задачу. `task-delivery` не пересчитывает project-start approvals и не решает, является ли дрейф factual или semantic.
Если Project Start активен, Task Delivery обязан оставить его канонические документы, ADR и все применимые `AGENTS.md` неизменными, записать `Canonical docs changed: NO` и описать предлагаемые изменения в `Proposed documentation maintenance`. Скрипт handoff сверяет это с фактическим снимком репозитория.

## Создание задачи

До `bootstrap` сформулируй один наблюдаемый результат и один связанный путь выполнения. Независимо принимаемые результаты являются разными задачами. `bootstrap` без `--apply` показывает будущие пути. С `--apply` он:

- создаёт машинное состояние в `.codex/task-delivery/<task-id>/state.json`;
- копирует новые заготовки в `<artifact-root>/<task-id>/`;
- отказывается перезаписывать существующие файлы;
- не меняет код, Git, трекер или внешнюю систему.

По умолчанию `artifact-root` равен `docs/tasks`. Если репозиторий уже использует другой каталог, передай его явно. Идентификатор должен быть устойчивым: номер задачи или короткое `kebab-case` имя.

Источник плана выбирается один раз при создании: `--plan-source LOCAL` или `--plan-source CANONICAL`. Второй вариант использует отдельную короткую заготовку-переходник. Скрыто менять владельца плана внутри уже созданной задачи нельзя.

## Режим `plan`

Разрешены чтение, диагностические команды, исходные тесты, внешнее исследование и создание артефактов задачи. Нельзя менять промышленный код, зависимости, схему данных или поведение приложения.

После `plan-review: PASS` состояние становится `awaiting_approval`. Верни пользователю:

- путь к плану и его SHA-256;
- итог независимой проверки;
- факты, допущения и открытые риски;
- точный идентификатор задачи для следующего вызова.

## Режим `implement`

Не создавай новую задачу. Выполни `status`, перечитай сохранённые артефакты и сравни текущие проектные договоры с теми, на которых строился план.

Новый явный запрос «реализуй этот план» сначала фиксируется через `begin-implement --apply` до любых правок `PLAN.md`. Он связывается с точными SHA-256 плана и обзора. Затем допустим `approve-plan --source user-invocation`. Если из-за дрейфа меняется `PLAN.md`, намерение аннулируется и нужен новый явный запрос пользователя. Не создавай новый `begin-implement` от имени старого сообщения.

Дрейф кода между этапами не всегда отменяет план. Исследуй его:

- если изменены планируемые швы, зависимости, данные или критерии, обнови внутреннее исследование, план и обзор;
- если изменение независимо и план остаётся тем же, зафиксируй факт в исследовании или `PROGRESS.md`, сохрани пользовательские правки и повторно проверь затронутый рубеж;
- если различить нельзя, остановись и покажи конфликт.

После одобрения `PLAN.md` неизменяем. Ход работы, неудачные гипотезы, лучшее известное состояние и команду возобновления записывай в `PROGRESS.md`; команда `checkpoint` связывает его с точным снимком реализации. Без свежего checkpoint нельзя фиксировать `verification`.

## Режим `full`

Начальный запрос разрешает перейти от проверенного плана к коду через `approve-plan --source full-mode-request`. Этот переход допустим только если:

- обзор проверял текущий SHA-256;
- `Critical open: 0` и `High open: 0`;
- объём не расширился после запроса;
- не появилось новое внешнее, разрушительное, дорогое или архитектурно необратимое действие.

Это разрешение расходуется один раз. Если после него план пришлось изменить и повторно проверить, продолжение требует нового явного запроса пользователя.

## Канонический план

Если GSD, трекер или проектный документ уже владеет планом, `PLAN.md` работает как переходник:

- `Plan source: CANONICAL`;
- точная ссылка, ID или путь;
- точная revision, commit или digest;
- область файлов и добавка проверки `task-delivery`;
- риски и условия остановки.

Не копируй весь канонический план и не веди две независимые отметки выполнения. `Plan source: LOCAL` допустим только при отсутствии владельца; тогда поля canonical равны `N/A`.

## Восстановление

После сжатия контекста или нового сеанса:

1. снова прочитай применимые инструкции;
2. выполни `inventory` и `status`;
3. перечитай только текущие доказательства и каноническую задачу;
4. возобнови первый незавершённый рубеж;
5. не полагайся только на сохранённый пересказ хука.

Если состояние повреждено, не переписывай его вручную. Сохрани файл, покажи ошибку и создай новую задачу только с другим идентификатором либо восстанови состояние осознанным исправлением скрипта.

Если процесс аварийно завершился и оставил lock, сначала выполни `recover-lock` без `--apply`. Команда разрешит удаление только для старого lock без живого PID; свежий или живой lock не трогается. Затем повтори с `--apply`. Не используй рекурсивное удаление lock.
