# Простота изменённого кода

Читай при существенной кодовой правке перед итоговыми проверками либо при задаче
рефакторинга/cleanup. Соблюдай project engineering standard и принятые контракты.
Это проход внутри Task Delivery, без отдельного controller или обязательного
cleanup-агента. Тривиальная правка получает соразмерный просмотр.

## Во время реализации

Автор сразу пишет по правилам проекта и проверяет наблюдаемое поведение.
Если выбран TDD, сохраняй RED → минимальный GREEN → refactor. В остальных
случаях следуй согласованному тестовому плану. Не откладывай понятные имена,
владение данными и обработку ошибок на будущего «чистильщика».

## Перед итоговой проверкой

Сравни собственную дельту с исходным baseline и реальными потребителями:

- есть ли лишняя обёртка без самостоятельной ответственности;
- уменьшает ли helper общую сложность вызовов или только длину одного файла;
- совпадают ли контракты похожего кода прежде, чем объединять его;
- остаётся ли shared небольшим и имеет ли новая зависимость реальную пользу;
- имеют ли модули связные обязанности, небольшие публичные интерфейсы и явного владельца состояния;
- можно ли изменить и проверить затронутую часть отдельно, без знания всей системы;
- не смешивает ли новый код интерфейс, бизнес-правила, хранение и внешние эффекты без обоснованной границы;
- можно ли яснее выразить ветвление, имя или владение состоянием;
- остались ли временные заглушки, обходы типов или мусор задачи.

Подтверждай пользу конкретным вызовом или сценарием. Сохранение понятного кода
без изменений — нормальный результат. Число строк, длина функции и количество
файлов являются сигналами для рассмотрения, а не самостоятельным оракулом.
Сохраняй публичное поведение, ошибки, эффекты, совместимость и оправданные защиты.

Сопоставь рост затронутых файлов/функций, ветвление и зависимости с baseline и
проектными ограничениями. Указывай смешанные обязанности, конкретный вызов или
сценарий изменения и подходящий шов. Не вводи универсальное число строк и не
выдавай перенос строк в несколько файлов за снижение сложности. Обоснованный
модуль может остаться крупным; legacy-узел не должен получать ещё одну несвязанную
обязанность только потому, что он уже большой. Generated/vendor учитывай по
правилам проекта. Неприменимость механической проверки или её будущая реализация
не означают, что автоматический контроль уже работает.

## Код без комментариев

ИИ не добавляет комментарии в код: inline/block, docstrings/JSDoc, TODO/FIXME и
закомментированный код. Выражай намерение понятными именами, типами, контрактами,
связными функциями и явным управлением потоком. Объяснения причин и использования
пиши в документации вне кода. Существующие лицензии и машинные директивы сохраняй;
старые комментарии за пределами правки массово не удаляй. Reviewer проверяет
фактическую дельту на соблюдение этого явного правила, даже когда код работает.

## Три разные операции cleanup

**Упрощение собственной правки** остаётся в её области. Не исправляй чужой
baseline и не разворачивай локальную задачу в общий рефакторинг.

**Удаление мёртвого кода** требует подтверждения: реальные entrypoints, публичные
потребители, динамические импорты, регистрации и framework conventions. Сначала
используй настроенный проектный анализатор, если он есть. Его отчёт даёт
кандидатов, а не разрешение удалить всё найденное. Удаляй узкими проверяемыми
партиями внутри выданного scope; новый анализатор не устанавливается автоматически.

**Завершение ресурсов** ограничено созданными текущим запуском временными
ресурсами. Worktrees, данные, containers/volumes, браузерные сессии и чужие
процессы имеют своих владельцев. Глобальная очистка не следует из завершения кода;
сохраняй действующие полномочия и предусмотренный native путь обслуживания.

## Автор, worker и reviewer

Обычно просмотр делает автор. Отдельный worker полезен для существенного
независимого объёма с точными owned paths и договором; назначение «cleanup»
само по себе не оправдывает делегацию. Одновременно действует один писатель
каждой области. Reviewer остаётся read-only и проверяет контракт, достаточность
тестов и оправданность структуры по текущей политике приёмки.

После упрощения выполни затронутые проверки на актуальном кандидате. Поздние
изменения делают зависимые результаты несвежими. Замечания исправляет автор
или назначенный worker; исправления возвращаются тому же reviewer в его scope.
Не запускай повторный полный цикл только из-за смены скилла.

Готовность: просмотрена собственная дельта, подтверждённые замечания устранены
или объяснены, нужные проверки актуальны. Запиши значимые решения и оставшиеся
риски в существующей задаче/review, без обязательного отдельного cleanup-отчёта.
