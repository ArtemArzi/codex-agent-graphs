# Оркестрация без лишних токенов

## Решение о делегации

Сначала спроси:

1. Есть ли ограниченный результат, который можно проверить независимо?
2. Может ли он выполняться параллельно с полезной работой корневого исполнителя?
3. Не требует ли он постоянного обмена состоянием с реализацией?
4. Сэкономит ли делегация больше времени и контекста, чем стоит запуск агента?

Если хотя бы два последних ответа неблагоприятны, работай локально.

## Обычная схема

```text
корневой исполнитель
├─ исследователь (только отдельный меняющийся внешний вопрос)
├─ проверяющий плана
└─ проверяющий результата
```

Исследователь не нужен, когда официальный документ можно прочитать одним адресным вызовом. Отдельный исполнитель кода не нужен, когда задача последовательна или затрагивает один шов.

Проверяющий плана и проверяющий результата — две самостоятельные области с
разными снимками и квитанциями. Без унаследованной acceptance policy запускай
каждую по её admission signal и не держи их одновременно: сначала обзор плана,
затем реализация, затем при фактическом риске обзор результата. При активной
policy свежий whole-plan reviewer обязателен до исполнения substantive плана,
а другой свежий whole-result reviewer — после кандидата; focused checks могут
идти рядом с соответствующим acceptor над тем же снимком. Все выбранные checks
должны завершиться до PASS, а root обязан сверить существенные findings с
исходниками.

## Пакет агенту

Каждый запуск получает самодостаточный пакет:

- цель и ожидаемый результат;
- точная область и исключения;
- пути и первичные источники, которые надо прочитать;
- подтверждённые факты и неизвестное;
- применимые инструкции, полномочия и запреты записи;
- критерии приёмки и команды проверки;
- формат ответа и уровни важности.

По умолчанию не передавай всю историю. Не наследуй Ultra в дочерний агент. Используй роль, заданную окружением: исследование/осмотр, реализация или обзор. Глубина — 1; потомки запрещены.

## Параллельная реализация

Разрешена только если части:

- имеют разные владельческие пути;
- не меняют общий договор одновременно;
- имеют независимые тестовые оракулы;
- могут быть объединены без скрытого порядка.

Не более двух пишущих агентов одновременно. Корневой исполнитель владеет общей архитектурой, интеграцией и итоговой проверкой. При грязном рабочем дереве предпочитай одного исполнителя.

Текущий короткий graph использует [implementation-slices.md](implementation-slices.md) внутри `work`, не добавляя узлов. `root-only` — fast path для domain work любого профиля; обязательные policy acceptors остаются операциями внутри `work`. Последовательный bounded slice нужен только когда независимая область реально экономит root-контекст или wall time. Этапы и слайсы сами по себе не требуют worker. Явный запрос на делегирование передаётся через `--implementation-strategy delegated-sequential`; `--slice-budget` в 3.9 — оценка, а не ограничение продолжения. Write-parallel fail-closed, пока runner не может доказать отдельные worktrees; разные названия директорий в общем checkout не являются изоляцией.

## Волна обзора

Verified Task Delivery запускает одного целостного проверяющего. Без
унаследованной policy несколько блочных проверяющих и целостный reviewer
допустимы только по явному deep/multi-review запросу; при активной policy
focused/block reviewers могут быть выбраны рядом с обязательным acceptor,
если каждый закрывает отдельный вопрос. Доступная ёмкость не является целью.

Все проверяющие получают один и тот же сырой снимок независимо. Корневой исполнитель:

1. проверяет сильные утверждения по реальным файлам;
2. объединяет дубли;
3. разрешает противоречия;
4. исправляет по важности;
5. возвращает тем же агентам только их область для подтверждения.

## Ограничители циклов

- не больше двух попыток одной гипотезы или сбоя;
- не запускать второго агента «на всякий случай»;
- не повторять работу агента из-за истёкшего ожидания — сначала проверить статус;
- не делать обзор обзора;
- не продолжать, если новый прогон не добавляет доказательств;
- после завершения области не переиспользовать агента для новой независимой работы;
- учитывать более строгие лимиты текущего `AGENTS.md`.

## Сжатие контекста

На границах сохраняй только:

- текущую фазу и SHA-256 доказательств;
- принятые решения;
- незавершённые риски;
- команды и их результат;
- следующий допустимый шаг.

Хуки памяти полезны для передачи, но машинное состояние и артефакты задачи остаются проверяемым основанием.
