# Проверка и независимый обзор

## Входной разбор и вопросы

Для существенной задачи до плана прочитай требования и документ роли `quality`
по карте документации. Для существенной задачи проверь применимость тем:
результат/границы и приёмка; роли/доступ; данные/совместимость; интеграции;
повторы, сбои и восстановление; нагрузка; выпуск/поддержка; бюджет/срок.
Используй известные ответы из переписки и проекта. Это внутренняя проверка
пробелов, не обязательная анкета при каждом запуске. Для тривиальной ясной
правки используй известные применимые правила и соразмерную проверку без
отдельного опроса, чтения всей карты или сообщения о рисках.

Спрашивай только когда неизвестное существенно меняет результат, риск или
приёмку и его нельзя выяснить чтением. Собери приоритетные вопросы в короткий
блок до зависимой работы; объясни последствия простыми словами, предложи
обоснованный вариант. Технический выбор тестов и инструментов сделай сам.
Пока ждёшь, выполняй независимую работу. Молчание не является согласием.
Повторно уточняй только новое существенное неизвестное.

При явном «без вопросов / сам реши» пропусти обычные уточнения.
Само слово «работай» не запрещает полезные вопросы. Продолжай
на основе известного, выбери обратимые допущения и кратко сообщи их. Не выдавай
предположение о бизнес-правиле, допустимой потере данных или бюджете за
согласованное. Отсутствие полномочий либо необратимое решение ограничивает
зависимое действие; остальную разрешённую работу продолжай. Не ослабляй
обязательный критерий, чтобы закончить задачу без вопросов.

## Выбор проверок и момента запуска

Оцени затронутые риски до реализации, затем выбери достаточные проверки.
Различай «требование определено», «проверка добавлена» и «проверка выполнена».

| Проверки | Когда добавлять/обновлять | Когда запускать |
| --- | --- | --- |
| Типы, линтер, сборка, структурные ограничения | При настройке стека/границ и изменениях конфигурации | Быстрые относящиеся проверки при разработке, обязательный набор в CI |
| Unit/компонентные | Вместе с новой или изменённой логикой/компонентом | После затронутых изменений; быстрый набор регулярно в CI |
| Интеграционные/контрактные | При появлении и изменении связи с БД, модулем, API | После изменения связи и на согласованном рубеже выпуска |
| E2E | Когда критический пользовательский маршрут доступен целиком | После затронутых изменений и перед выпуском по политике проекта |
| Регрессия | Сохранить нужные проверки функций; при баге добавить воспроизведение причины | При изменениях выполнять относящийся набор, перед выпуском — согласованный набор |
| Нагрузка/стресс/длительная работа | Когда доступны сценарий и обоснованный профиль нагрузки | До существенной нагрузки, после изменений производительности/ёмкости, по проектному графику |
| Отказы, повторы, конкурентность, перезапуск | Вместе с зависимостями, очередями и механизмами повторов/сохранения | При изменении этих механизмов и до их ввода в эксплуатацию |
| Резервные копии/восстановление | Вместе с хранением и резервированием | Реальное восстановление до признания готовности, после изменений и периодически |
| Права/безопасность | Вместе с ролями, доступом, входными данными и внешними границами | При затронутых изменениях; сканеры по CI/графику, целевые проверки по риску |
| Миграции/совместимость | Вместе с изменением схемы, формата данных или публичного API | До выпуска на репрезентативных обезличенных данных; проверить допустимый путь восстановления |
| Визуальные/доступность/браузеры | При изменении пользовательского интерфейса | Для затронутых состояний/устройств и на рубеже выпуска |
| Smoke | При подготовке пути развёртывания | После каждого развёртывания в доступном разрешённом окружении |
| Приёмочные | Критерии до реализации, сценарии вместе с функцией | Когда готов пользовательский результат; человек участвует согласно договору проекта |
| Evals агента | Сценарии и критерии до изменения AI-поведения | При изменении модели, инструкций, инструментов/контекста; учитывать вариативность повторными попытками |

Категории пересекаются: регрессия может состоять из unit/integration/E2E.
Не добавляй дубликат теста только ради нового ярлыка. Выбирай по последствиям
сбоя и изменённым границам; все строки не обязаны исполняться в каждой задаче.
Пороговые значения бери из проекта или обоснованного допущения с явной меткой.
Нагрузочные и отказные эксперименты проводи в подходящем разрешённом окружении;
таблица сама по себе не разрешает воздействие на production.

В существующем плане или рабочем контексте фиксируй компактно:
`риск/требование → проверка → добавить/переиспользовать → момент/окружение → критерий`.
Для отложенного укажи причину, конкретный следующий рубеж и последствие для
готовности; для неприменимого достаточно короткого обоснования там, где оно
неочевидно. Если документа качества нет, используй существующие требования,
сохрани нужные решения в текущем плане и передай документальный пробел в
Project Start. Это не запускает полный bootstrap ради локальной правки.
Передай исполнителям/проверяющим относящиеся требования и путь к их владельцу.

Для существенной задачи до работы напомни простыми словами, что может сломаться и что
проверишь. В конце раздели выполненное, не прошедшее и непроверенное, назови
окружение/ссылку на evidence и ограничения выпуска. Если поменялись постоянные
требования или команды, актуализируй их владельца через существующий маршрут
документации. Непроверенный обязательный критерий не считается выполненным;
локальные тесты не доказывают деплой, восстановление, доставку или человеческую
приёмку. Наличие текста инструкции не доказывает фактическое чтение агентом.

## Оракул до реализации

Для каждого критерия приёмки заранее выбери наблюдение, которое отличает правильный результат от неправильного. Предпочитай публичный шов:

- функция или модуль — его интерфейс;
- API — запрос и ответ плюс побочные эффекты;
- интерфейс — реальный пользовательский путь;
- очередь/задача — состояние до и после, повтор и ошибка;
- миграция — данные до/после, совместимость и откат;
- агент/подсказка — набор случаев, метрика и защита от обхода оценщика.

Не измеряй только внутренние вызовы, если требование описывает поведение.

## Применимый набор доказательств

Выбирай относящиеся пункты по матрице выше и требованиям проекта. Это набор
возможных доказательств, а не обязательные восемь действий для любой правки.

1. Исходное состояние: тест или воспроизведение до изменения.
2. Быстрый цикл: узкая проверка после каждой сквозной части.
3. Полный применимый набор: тесты, типы, линтер, сборка, архитектурные проверки.
4. Дымовой путь через реальный вход.
5. Негативный и пограничный случай.
6. Активная попытка опровергнуть решение.
7. Проверка нового теста как оракула.
8. Итог хуков и CI, если доступны.

Для каждого запуска сохрани команду, каталог, назначение (`positive`, `negative`, `baseline` или `diagnostic`), дату, наблюдаемый код завершения, допустимые ожидаемые коды, признак совпадения с ожиданием и краткий результат. Нужен хотя бы один положительный оракул с кодом 0. Коды 126/127 означают, что команда не была исполнима, и не являются проверкой. Ненулевой код допустим только для заранее ожидаемого исходного или негативного сценария. Не вставляй гигантский вывод; сохрани адресный фрагмент или ссылку на артефакт.

До запуска проверь существующие команды проекта и наличие раннера. Отсутствие `pytest`, Playwright или другого инструмента не даёт права устанавливать его без разрешения. Используй объявленный проектом запасной раннер либо отметь проверку заблокированной.

## Проверка нового или сгенерированного теста

Используй хотя бы один способ:

- тест падает на исходной ошибке и проходит после исправления;
- тест падает на маленьком намеренно неверном изменении;
- тест проходит на известной правильной версии и падает на известной неправильной;
- для свойства показан конкретный контрпример.

Если это невозможно, отметь тест как слабое доказательство и добавь другой оракул. Не меняй эталон только ради зелёного результата.

## Активный проверяющий

Проверяющий не повторяет тесты механически. Он выбирает наиболее вероятный способ обмануть результат:

- пропущенная ветка ошибки или пустое значение;
- повторный запрос, гонка, тайм-аут, отмена;
- несовместимая старая запись или версия клиента;
- скрытый побочный эффект;
- тест, который проверяет собственную заглушку;
- отключённый, переименованный или чрезмерно ослабленный тест;
- дублированный помощник вместо использования существующего шва;
- несоответствие документации и фактического поведения.

Найденный контрпример превращай в воспроизводимую проверку, если он устойчив и относится к договору.

## Карта независимого обзора

При унаследованной policy простое инженерное изменение получает одно итоговое
`block_reviewer`; обычные неинженерные ревью используют эту же роль. Только
complex engineering / material risk требует `task_plan_reviewer` и другого
`task_result_reviewer`. Смена этапа/skill не запускает эту пару заново. Root self-review, slice
acceptance и controller receipt не заменяют эту независимость. Focused/block
checks могут выполняться рядом с acceptor над тем же кандидатом; PASS возможен
только после завершения всех выбранных checks и reconciliation существенных
findings с первичными источниками. Без такой policy действует матрица
risk-based fallback ниже.

Сначала составь непересекающиеся поверхности:

- поведение и критерии;
- архитектура и зависимости;
- данные, совместимость и миграции;
- безопасность и полномочия;
- надёжность, параллелизм и производительность;
- интерфейс и доступность;
- тесты, CI и наблюдаемость.

Не создавай проверяющего на каждую поверхность. Группируй по реальному риску:

- `P3`: сокращённый набор доказательств и self-review без унаследованной
  policy; при активной policy простое инженерное изменение получает одно
  `block_reviewer`, обычные document reviews тоже auxiliary, trivial chat — root-only;
- `P2`: self-review по умолчанию без унаследованной policy; один целостный
  проверяющий только при uncertainty, неполных тестах, публичном контракте или
  отдельной поверхности риска, а policy-required whole reviews обязательны
  независимо от этой матрицы;
- `P1`: целостный проверяющий и 1–2 блочных по независимым рискам;
- `P0`: целостный обзор и отдельный обзор причины/предотвращения повторения; аварийное ограничение ущерба находится вне этого навыка и не отменяет его рубежи ремонта.

Проверка плана и проверка результата — разные области ответственности. Для них нужны отдельные запуск и разные квитанции; не переиспользуй исполнителя проверки плана как проверяющего результата без нового запуска в новой области. Обычно держи активным одного из них, потому что эти этапы последовательны. Машинный список результата требует `whole-system`; для `P1` ещё `risk-block`, для `P0` ещё `root-cause`.

Целостный проверяющий отвечает за связи между блоками, полный путь, последовательность выпуска и пробелы доказательств. Блочный не выходит за назначенную область. Они не читают ответы друг друга до общей сводки.

## Архитектурная приёмка

Сравни код одновременно с требованиями пользователя, принятым планом и
исходными архитектурными документами проекта. Проверь границы модулей,
публичные интерфейсы, владельцев данных и транзакций, направления зависимостей,
новые общие пакеты и обходы через БД/события. План не разрешает нарушение
канонического правила только потому, что это нарушение не заметили раньше.

Проверь актуальность документов, переданных исполнителям, и разрешение каждого
обнаруженного архитектурного исключения. Установи, что команды качества реально
выполнены, а запланированные проверки не выданы за работающие. Для нового
архитектурного теста покажи известное нарушение, на котором он падает. Проверка
импортов не доказывает корректность динамических связей через БД или события.
Объём проверок определяется затронутыми границами и риском, а не количеством
папок. Семантическое соответствие оценивает reviewer; digest доказывает только
целостность прочитанного документа.

## Разрешение замечаний

- `Critical` и `High` блокируют завершение.
- `Medium` исправляй, если относится к договору и не расширяет задачу; иначе зафиксируй решение и владельца.
- `Low` не должен превращать задачу в косметическую переработку.

После исправлений повтори затронутые проверки и попроси тех же проверяющих подтвердить только их область. Один повтор обычно достаточен. Если замечание повторяется без новых фактов, остановись и покажи спор или блокер пользователю.

## Завершение

Для tracked/verified работы `task.json`, `verification.json` когда его требует
controller, и `HANDOFF.md` должны позволять другому человеку ответить. При
унаследованной policy нужен verdict выбранной по глобальному порогу роли:
`block_reviewer` для простого engineering/ordinary non-engineering review либо
whole acceptance для complex engineering / material risk. Native verdict не
требует controller; несовместимые старые runs обрабатывай по Controller
compatibility в SKILL.md, не выдавая их за verified/complete.

- что фактически запускалось;
- какое исходное и итоговое поведение наблюдалось;
- пытались ли сломать результат;
- почему новым тестам можно доверять;
- что проверили независимо;
- какие риски остались и как откатиться.
