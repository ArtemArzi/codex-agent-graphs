# Task Delivery

Доведи одну уже очерченную задачу от фактов до проверяемого результата. Подстраивайся под действующий репозиторий, навыки, MCP, плагины и хуки; не создавай параллельную систему управления проектом.

Команды требуют Python 3.10 или новее. На Unix используй `python3`, на Windows — `py -3`. Запускай их из каталога этого навыка.

## Выбери режим

- `plan` — исследуй, создай план, проведи независимый обзор и остановись. Промышленный код не меняй.
- `implement` — возьми существующий проверенный план. Новый явный запрос сначала привяжи к точным SHA-256 плана и его обзора через `begin-implement`; только затем проверяй дрейф. Если из-за дрейфа пришлось изменить `PLAN.md`, старый запрос больше ничего не разрешает: остановись и дождись нового явного запроса.
- `full` — исследуй, проверь план и сразу реализуй его. Первоначальный явный запрос разрешает перейти к реализации после `PASS`, но не разрешает скрыто расширять объём, писать во внешние системы, менять архитектурное основание, выполнять разрушительные действия или выпускать в производство.

Если режим не назван, выведи его из формулировки. Для неоднозначного запроса начни с `plan`. Приоритет пользователя сохраняй как есть; если его нет, используй `P2` для обычной задачи, `P1` для высокого риска и `P3` для документации или локальной косметики.

## Неподвижные правила

1. Сначала прочитай применимые инструкции, документы, состояние проекта и исходный путь выполнения. История разговора не заменяет текущее состояние файлов.
2. Соблюдай иерархию: системные и средовые правила → применимые `AGENTS.md` и договоры навыков → прямой запрос пользователя → каноническая задача, спецификация и проектные договоры → локальные доказательства `task-delivery`. Нижний уровень не переопределяет верхний. Не создавай второй источник истины.
3. Перед исследованием выполни рубеж возможностей: доступные навыки, реально вызываемые MCP и инструменты, плагины, хуки, полномочия и безопасные запасные пути.
4. Доступный и относящийся к задаче MCP используй обязательно, если он даёт приватные или живые данные, официальную текущую документацию, сведения из трекера, работу с интерфейсом либо проверку реальной системы. Не вызывай MCP ради количества.
5. Настроенный MCP ещё не значит доступный. Сверяй конфигурацию с каталогом инструментов текущего запуска. При разрыве явно укажи его и используй безопасный запасной путь.
6. Хуки являются обязательной инфраструктурой. Не обходи, не отключай и не дублируй их. Предупреждение или блокировка хука — это рубеж, а не помеха.
7. Всегда проведи внутреннее исследование. Внешнее исследование проводи по первичным источникам, когда решение зависит от библиотеки, протокола, платформы, безопасности или меняющегося факта; для чисто внутреннего изменения зафиксируй `N/A` с причиной.
8. Плохой план хуже отсутствующего: до кода план должен получить независимый `PASS`, не иметь открытых `Critical` и `High` и ссылаться на точный SHA-256 проверенной версии.
9. Реализуй небольшими сквозными частями. После каждой сохраняй лучшее известное состояние через работающие проверки и доказательства; коммит или ветку создавай только когда это разрешено.
10. Проверяющий пытается опровергнуть решение: ищет контрпример, обход теста, неверную обработку ошибки, регрессию на соседнем пути и расхождение с договором.
11. Новый или сгенерированный тест сам нуждается в проверке: покажи, что он падает на исходной ошибке или заведомо неверном варианте и проходит после исправления. Иначе не считай его оракулом.
12. Повторяемое исправление превращай в тест, тип, линтер, архитектурную проверку, наблюдаемость или короткое правило. Не ограничивайся записью в отчёте.
13. Не объявляй готовность без выполненных команд, кодов завершения, независимого обзора и перечисленных остаточных рисков.
14. Ограничивай стоимость: один исполнитель по умолчанию, делегация только для независимой работы, глубина 1, ограниченные пакеты контекста и остановка цикла, если новый прогон не даёт новых доказательств.

## Начало каждого запуска

1. Найди корень репозитория. Прочитай применимые `AGENTS.md`, `CLAUDE.md`, `CONTEXT.md`, спецификацию, ADR, задачу и карту документации. Проверь грязное рабочее дерево и не присваивай изменения пользователя.
2. До создания состояния сформулируй один наблюдаемый результат и один связанный путь выполнения. Если запрос содержит несколько независимо принимаемых результатов, раздели их на разные задачи.
3. Выполни адресный безопасный осмотр. Передай 1–3 поисковых термина через `--match`, а второй Codex home — через повторяемый `--codex-home`, только если он действительно используется:

   ```bash
   python3 scripts/task_delivery.py inventory --root <repo> --match <стек-или-система>
   python3 scripts/task_delivery.py status --root <repo> --task-id <id>
   ```

4. Если есть состояние `project-start`, выполни его `status`. Работай этим навыком только на этапе реализации; иначе вернись к допустимому рубежу `project-start`.
5. Если у репозитория уже есть GSD, собственный трекер или каталог задач, используй его как источник состояния. Локальные артефакты `task-delivery` являются доказательствами конкретной задачи, а не новым планом всего проекта.
6. Если состояния задачи нет, сначала покажи предварительный просмотр, затем создай новые файлы. Выбери существующий каталог задач; при его отсутствии используй `docs/tasks`:

   ```bash
   python3 scripts/task_delivery.py bootstrap --root <repo> --task-id <id> --title "<название>" --outcome "<один наблюдаемый результат>" --mode plan --priority P2
   python3 scripts/task_delivery.py bootstrap --root <repo> --task-id <id> --title "<название>" --outcome "<один наблюдаемый результат>" --mode plan --priority P2 --apply
   ```

   Для полного цикла укажи `--mode full`. Если планом уже владеет GSD, трекер или проектный документ, при обоих вызовах добавь `--plan-source CANONICAL`; иначе действует `LOCAL`. Не перезаписывай существующие артефакты. В режиме `implement` не создавай новую задачу: открой прежнее состояние.

Подробные переходы и восстановление описаны в [references/workflow.md](references/workflow.md).

## Рубеж возможностей

Прочитай [references/capability-routing.md](references/capability-routing.md). Заполни `CAPABILITIES.md` до основного исследования:

- какие инструкции и хуки действуют;
- какие относящиеся к вопросу навыки, обычные инструменты, MCP и приложения объявлены и какие реально вызываются; не составляй полный каталог окружения;
- что выбрано, для какого вопроса, с каким доступом и внешним последствием;
- какой есть запасной путь;
- что выглядело подходящим, но намеренно не выбрано;
- чего не хватает.

Если в текущей поверхности есть поиск инструментов, используй его для обнаружения нужного приложения. Для приложений не перечисляй MCP-ресурсы и шаблоны; для обычного MCP читай ресурсы только когда сервер действительно публикует относящийся к задаче материал. Перед зависимостью от выбранного MCP, приложения или браузера выполни минимальный безопасный вызов только на чтение и сохрани квитанцию. Для хуков различай `configured-only` и реально `observed`.

Не устанавливай плагин, не включай MCP и не меняй разрешения без явного согласия. Внешние записи в GitHub, Linear, Notion, Drive, Jira и другие системы требуют отдельного разрешения, если пользователь прямо их не запросил.

```bash
python3 scripts/task_delivery.py record --root <repo> --task-id <id> --event capabilities --evidence <CAPABILITIES.md> --note "<выбранный набор>" --apply
```

## Исследование и план

1. Внутреннее исследование: проследи реальный путь выполнения, публичные швы, данные, ошибки, тесты, ближайшие аналоги и исходное поведение. Сохрани факты отдельно от выводов и предположений.
2. Внешнее исследование: начни с официальной документации, исходного кода, спецификации или статьи авторов. Используй `research`, когда полезна отдельная ограниченная работа по первичным источникам; его фоновый агент и запись подчиняются полномочиям и лимитам этого навыка.
3. Зафиксируй исходную проверку или воспроизведение. Если ошибка не воспроизводится, не маскируй неопределённость планом.
4. Если планом уже владеет GSD, трекер или другой канонический файл, укажи `Plan source: CANONICAL`, точную ссылку/ID и revision/digest. Не копируй его: добавь только область, оракулы, риски и условия остановки. Полный локальный договор создавай лишь при `Plan source: LOCAL`.
5. Для `LOCAL` заполни `PLAN.md` как полный исполняемый договор: цель, критерии приёмки, исключённое, путь выполнения, выбранное решение и отвергнутая альтернатива, сквозные части, риски, проверки, документация и условия остановки. Для `CANONICAL` оставь только переходник из предыдущего пункта.
6. Не планируй по слоям «сначала база, потом сервер, потом интерфейс», если часть не даёт наблюдаемого поведения. Каждая часть должна иметь собственный оракул.

Подробный договор читай в [references/planning-contract.md](references/planning-contract.md).

```bash
python3 scripts/task_delivery.py record --root <repo> --task-id <id> --event internal-research --evidence <INTERNAL-RESEARCH.md> --apply
python3 scripts/task_delivery.py record --root <repo> --task-id <id> --event external-research --evidence <EXTERNAL-RESEARCH.md> --apply
python3 scripts/task_delivery.py record --root <repo> --task-id <id> --event plan --evidence <PLAN.md> --apply
```

Передай план независимому проверяющему без ожидаемого ответа. Он сверяет намерение пользователя, код, документы, внешние источники, минимальность решения, выполнимость проверок и выбранные возможности. Заполни точный SHA-256 плана в `PLAN-REVIEW.md`, исправь существенные замечания и запиши результат:

```bash
python3 scripts/task_delivery.py record --root <repo> --task-id <id> --event plan-review --evidence <PLAN-REVIEW.md> --apply
```

Квитанцией служит фактический идентификатор отдельного агента/задачи, запуск `/review` или имя человека с датой. Скрипт проверяет наличие и связь квитанции с SHA, но не может криптографически доказать авторство — корневой исполнитель отвечает за то, что квитанция получена реально, а не придумана. Если независимый проверяющий недоступен, не заполняй `PASS`: оставь состояние на `next_event=plan-review`, назови блокер и точную команду возобновления. Не проверяй собственный план «независимо».

- В `plan` остановись со статусом `awaiting_approval` и покажи план, вывод проверки, риски и точную команду продолжения.
- В `full` после `PASS` зафиксируй переход без повторного вопроса: `approve-plan --source full-mode-request`.
- При последующем `implement` сначала, до любых правок плана, привяжи новый запрос к текущим SHA через `begin-implement`. Затем разрешён `approve-plan --source user-invocation`.

```bash
python3 scripts/task_delivery.py begin-implement --root <repo> --task-id <id> --note "<источник/ход и точный смысл запроса без секретов>" --apply
python3 scripts/task_delivery.py approve-plan --root <repo> --task-id <id> --source <full-mode-request|user-invocation> --note "<что разрешено>" --apply
```

Если после `begin-implement` меняется `PLAN.md`, не создавай новый `begin-implement` от имени старого сообщения. Покажи новый SHA и попроси новый явный запрос пользователя. Разрешение режима `full` расходуется один раз; после последующего изменения плана тоже нужен новый запрос.

Для `CANONICAL` независимая проверка плана фиксирует точную revision, источник, квитанцию read-only проверки и время. Перед итоговой проверкой обнови эту квитанцию в `VERIFICATION.md`; изменение revision означает остановку и возврат к владельцу плана.

## Реализация

1. Повтори `status`. Если план, его обзор или применимые договоры изменились, не продолжай по старому одобрению. Исследуй дрейф и повторно проверь затронутую часть.
2. Работай по одной сквозной части. Сначала минимальное изменение поведения, затем быстрый оракул, затем следующий шаг.
3. Используй `prototype` только для одного неопределённого вопроса и в явно одноразовой области. Не следуй его правилу о ветке или коммите без полномочия.
4. Используй `codebase-design`, если меняется шов, интерфейс, направление зависимости или форма модуля. Не запускай архитектурную переработку для локальной правки.
5. Подбирай стековые и качественные навыки условно: `coding-standards`, `eval-harness`, `ai-regression-testing`, `e2e-testing`, навыки безопасности и официальные практики стека. Проектные правила имеют приоритет; отсутствие навыка не отменяет требуемую проверку.
6. Не меняй тест только потому, что он мешает реализации. Объясни изменение договора и покажи, что новый тест различает правильное и неправильное поведение.
7. После каждой существенной части перечитай неизменяемый утверждённый план, обнови `PROGRESS.md`, сравни фактический объём с разрешённым и сохрани рубеж:

   ```bash
   python3 scripts/task_delivery.py checkpoint --root <repo> --task-id <id> --apply
   ```

   Не используй `PLAN.md` как журнал. Перед `verification` нужен свежий рубеж точного снимка кода.

## Проверка, обзор и завершение

Прочитай [references/testing-and-review.md](references/testing-and-review.md) и [references/orchestration.md](references/orchestration.md).

1. Выполни исходную и итоговую проверку, быстрый набор, полный применимый набор, типы/линтер/сборку и реальный дымовой путь. Неприменимое пометь с причиной. Сначала проверь, какие команды и раннеры действительно объявлены и доступны. Не устанавливай отсутствующий раннер незаметно; используй предусмотренный проектом запасной путь или зафиксируй пробел.
2. Проведи активную проверку контрпримером. Для интерфейса проверь реальное поведение через доступный браузерный MCP; для API — публичный шов; для миграции — прямой и обратный путь; для агента — набор оценок и обход оракула.
3. Зафиксируй команды, коды завершения, проверку новых тестов, результаты хуков и остаточные риски в `VERIFICATION.md`.
4. Проведи независимый обзор изменений. Проверка плана и проверка результата — две разные области и два отдельных запуска; обычно они идут последовательно, по одному активному проверяющему. По умолчанию для результата достаточно одного целостного проверяющего. Добавляй проверяющих отдельных блоков только для действительно независимых поверхностей риска; они не проверяют друг друга.
5. Исправь `Critical` и `High`, повтори затронутые проверки и один раз попроси тех же проверяющих подтвердить исправление. Не создавай цепочку «обзор обзора».
6. Обнови только затронутую документацию и `HANDOFF.md`. Не переписывай историю проекта.

```bash
python3 scripts/task_delivery.py record --root <repo> --task-id <id> --event verification --evidence <VERIFICATION.md> --apply
python3 scripts/task_delivery.py record --root <repo> --task-id <id> --event code-review --evidence <CODE-REVIEW.md> --apply
python3 scripts/task_delivery.py record --root <repo> --task-id <id> --event handoff --evidence <HANDOFF.md> --apply
python3 scripts/task_delivery.py complete --root <repo> --task-id <id> --apply
```

Заверши кратко: что изменено, чем доказано, какие MCP и навыки реально использованы, что сделали хуки, что осталось рискованным и какой следующий шаг разрешён.

## Ограничение стоимости и делегации

- Обычная задача: корневой исполнитель, при необходимости один исследователь и обычно один активный проверяющий одновременно; проверка плана и проверка результата запускаются отдельно.
- Реализацию не дроби между агентами, если части связаны. Не более двух пишущих агентов и только при независимых владениях.
- Для `P2/P3` начни с одного целостного проверяющего; добавь блочного только при отдельном риске. Для `P1` обязательны целостный и отдельный риск-проверяющий; для `P0` — целостный и отдельный проверяющий причины/предотвращения. Их уникальные квитанции записываются в машинном блоке `CODE-REVIEW.md`.
- Наследуй более строгий лимит из `AGENTS.md`. Держи глубину 1, не передавай полную историю из Ultra, давай самодостаточный пакет с путями, ограничениями, критериями и форматом ответа.
- Ограничь одну гипотезу двумя попытками. Если повтор не даёт новой информации, остановись, сохрани лучшее известное состояние и назови блокер.
- Не запускай одинаковое исследование двумя агентами и не создавай агента на каждый файл.

Основания этих правил и первичные источники собраны в [references/research-basis.md](references/research-basis.md).

## Служебные ресурсы

- `scripts/task_delivery.py` — безопасный осмотр, создание, состояние, отпечатки и рубежи.
