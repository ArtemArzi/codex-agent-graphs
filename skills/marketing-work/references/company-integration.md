# Встроить метод в существующую компанию

Читай только для Company Work System или аналогичной среды с собственными правилами результата. Этот адаптер - инструкция использования внешнего метода внутри подготовки; он не изменяет код/стандарты компаний и не добавляет locally resolvable workflow dependencies.

## Выбрать владельца

1. По карте Work перейди в фактический корень выбранной компании. Прочитай её AGENTS, config, README, marketing/brand/source маршрут и существующее дело. Проверку общей версии выполняй с частотой местного процесса, а не заново на каждом методическом шаге.
2. Установи company/brand identity и применимые принятые определения. В многобрендовом бизнесе различай материал, активы, аудиторию и источник каждого бренда. Совместный материал должен явно содержать основания обеих сторон, а не общую выдуманную persona.
3. Прочитай местный `company-marketing` и его парный workflow, если они есть. При наличии местного SMM/research/content/analytics навыка используй его принятую специализацию. Глобальные маркетинговые методы помогают в фазе подготовки; существующие company skills владеют записью и проверкой.

Реальные пути и доступность устанавливай в текущей компании. Не создавай одинаковые context.md/marketing-plans/STATUS поверх принятого владельца. Существующие карточки контента и клиентские задачи сохраняют статусы.

## Подготовить результат по текущему контракту

Прочитай текущую местную схему/пример перед записью. В наблюдённом Result v1 маркетинга содержатся:

| Поле результата | Смысл |
| --- | --- |
| company_id, kind, summary, next_action, limitations | Идентичность, полезный выход, продолжение и предел |
| sources с относительными путями и hash | Принятые первичные факты из этой компании, а не глобальная методичка |
| audience, recipient_action, material | Кому адресовано, какое действие, что подготовлено |
| measurement_source, neighbor_handoff | Где наблюдать результат и кто принимает соседний шаг |
| proposal_status + допустимый decision_id при принятом решении | Черновик не объявляется действующей политикой |
| budget_status, publication_status | Действительные состояния бюджета/публикации по местной схеме |
| application_status, effect_status | Для нового внутреннего артефакта остаются unknown |

Это наблюдённая версия, не альтернативная схема. Используй текущие местные имена/допустимые значения. Принятое здесь предложение не доказывает применения и эффекта. Название глобального навыка может быть методическим provenance, но не подменяет фактологический источник компании. Абсолютный global SKILL path не становится допустимым client source.

Для показателей проверь местный source contract: account/scope, период, единицы, полноту, свежесть и область доступа. При пустом источнике в config данные не становятся принятыми только потому, что MCP подключён. Доступное локальное наблюдение можно обозначить именно так и подготовить недостающую спецификацию источника.

## Сохранить намерение и конкурентные изменения

При подготовке сохраняемого результата один раз прочитай task/context либо ответ intake/decide и сохрани текущую revision. Передавай её существующему execute как expected revision вместе с точным кандидатом и требуемой проверкой. Если версии изменились, перечитай и сопоставь изменённые факты с намерением, затем заново подготовь затронутый кандидат. Подстановка новой revision в старый результат обходит смысловую сверку.

Используй действующие команды компании. После execute проверь сохранённый output, его hash и актуальное состояние чтением task/context. Это readback записи, он не доказывает применение или эффект.

Observe записывает наблюдение только слоя application или effect по отдельному свидетельству владельца. Это не команда чтения или обязательный шаг после execute. Для такой записи нужны настоящее свидетельство нужного слоя, действующий actor, актуальная revision и точный result SHA по местному контракту. При отсутствии свидетельства application/effect остаются unknown; доставку разрешённого результата можно выполнять отдельно. Не записывай фиктивное наблюдение ради завершения.

Не исправляй task.json вручную ради обхода отказа и не помечай CLI вызов состоявшимся без его выполнения. При недоступной среде оставь готовый артефакт и конкретный следующий шаг, без выдуманного receipt.

Доставка в приватный Git, публикация в канал, работа команды и коммерческий эффект - разные события с разными правами. Сохраняй только точные собственные разрешённые пути штатным способом компании. Данные одной компании, её клиенты, цены, сырьё и активы не переносятся в общий пакет или другую компанию.
