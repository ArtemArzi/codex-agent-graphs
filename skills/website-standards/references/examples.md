# Independent profiles

| Request | Applicable work and boundary |
| --- | --- |
| “Яндекс и Метрика, заявки в нашей CRM” | Yandex SEO + exact Webmaster site/Metrika counter; existing CRM acceptance/retry/recovery and mobile path. No automatic Google accounts or second lead model |
| “Google, маленький static site, backend нет” | Google SEO/GSC; GA4 only if selected. Compare existing native/managed inbox first. Provider acceptance does not establish undocumented physical durability/idempotency |
| “Оба поисковика, заявки в таблицу и Telegram” | Common URL contract plus independent account observations. Compare provider versus existing DB/outbox. Sheets business-ID reconciliation, Telegram ambiguity. No multilingual pages without actual variants |

External booking is a different contour: a click may be `booking_started`,
while `booking_confirmed` requires the authoritative booking system and permitted
access. Do not build a backend merely because the public site is platform-hosted.

An existing clean source check can coexist with unverified live ACL/provider
delivery. Report those boundaries instead of repeating unrelated full tests or
inventing a global “ready” score.
