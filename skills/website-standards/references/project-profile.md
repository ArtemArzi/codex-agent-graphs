# Map the actual project

Use known context first. Select business goal and market with the user only when
unknown and consequential; choose routine mechanisms/test names as the agent.

| Input | Recover from existing owners |
| --- | --- |
| Scope | Critical visitor task, public/private routes, market/language, selected search engines |
| Identity | Repo/candidate/artifact, staging/production origin, URL and redirect inventory |
| Measurement | Selected services independently of search; property/stream/counter bindings, roles, events, consent and environment policy |
| Intake | Current provider/CRM/system of record, required fields, validation, consent, receipt/key semantics, delivery destinations, manager role |
| Recovery | Storage/volume, retention/dedup window, retry ambiguity policy, alerts/owner, backup and agreed RPO/RTO |
| Verification | Existing quality/runbook owners, native commands, fixtures, original evidence and live-check triggers |

Unknown spending limits, retention, loss tolerance and response time remain
unknown/proposed. Do not infer legal approval from a checked consent box. No
database/payment/provider requirement is added to a site that does not use it.

Keep the mapping in existing architecture/quality/deployment documents. A small
machine-readable profile is optional and points to them; it is data, not shell
code or a second controller. Avoid an exhaustive client questionnaire. Partial
profile evidence can support bounded work without claiming complete readiness.
