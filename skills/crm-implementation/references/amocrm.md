# Ветка amoCRM

Читай для настройки и интеграций amoCRM. Сначала установи реальный домен аккаунта и продукт; Kommo и российский amoCRM нельзя считать взаимозаменяемыми только по похожим объектам API.

## Установить подключение и покрытие

Проверь доступные инструменты текущего чата, их схемы, пользователя/права, тарифные ограничения и способ авторизации. Сохрани работающий разрешённый MCP или другой транспорт. При отсутствии инструмента подготовь модель и проверяемый запрос/план, обозначь недоступную операцию; новый аккаунт/коннектор или секрет не возникает автоматически из установки скилла.

Проверяй отдельно нужные операции: чтение/изменение записей, создание/изменение воронок и стадий, определение полей, роли, подписки и автоматизации. Наличие чтения полей в MCP не доказывает возможность их создания. Отсутствие нужной операции в одном MCP не означает её отсутствия в API платформы.

Устанавливаемый технический кандидат должен соответствовать домену и нужным операциям. Например, если код строит адрес только через `kommo.com`, для *.amocrm.ru нужна отдельная проверенная адаптация. Название «amoCRM/Kommo» или большой счётчик инструментов этого не заменяет.

## Работать с реальными метаданными

Перед изменением получи актуальные воронку/стадии, пользователей, определения полей и варианты перечислений нужного аккаунта. Сущности сделки, контакта, компании, задачи и примечания имеют разные контракты; не переноси идентификаторы и формы между ними или другими клиентами.

Для API v4 проверь форму конкретного запроса: ряд bulk-операций использует массив объектов, а одиночное изменение/другая операция может использовать объект. Телефон и email контакта в соответствующих методах передаются через пользовательские поля, а не выдуманные верхнеуровневые свойства. Типы/enum ID бери из метаданных.

Ответы списков могут содержать HAL `_embedded` и `_links`, а MCP может их нормализовать. Сверяй реальную схему ответа; проходи нужные страницы по объявленной пагинации и не считай первую страницу полной базой. Ограничения фильтров и объёма проверяй для метода/аккаунта.

После записи перечитай объект, поля, ответственного, связи и нужное состояние. В API наличие `request_id` само по себе не доказывает защиту от дублей: установи документированную семантику. Повторное обращение клиента не всегда требует объединения сделок.

## События, авторизация и проверка

Для вебхуков установи, какие события доступны и что реально приходит: идентификаторы, состояние, возможные повторы и порядок. По необходимости дочитывай актуальный объект и сверяй итог. Подписка не доказывает доставку; приём события не доказывает запись в получателе. Обработка повторов и восстановление описаны в [интеграциях](integrations.md).

Различай OAuth с механизмом обновления и токен длительного действия. Для отозванного или истёкшего доступа выясни поддерживаемый способ восстановления; не повторяй бизнес-запись вслепую после обновления доступа. Точные лимиты, коды ошибок и тарифные условия сверяй перед реализацией, не зашивай фиксированные числа в общий цикл.

Проверь обычный сценарий и существенное исключение под нужной ролью, конечные записи обеих систем и передачу следующему сотруднику. Отдельно установи включение робота/Salesbot/другой автоматизации, если она входит в задачу; технический вызов настройки не доказывает её фактическое действие.

Для исправления кода используй инженерный цикл, для неверных полей/автоматизаций — эту ветку, для изменения бизнес-правила — владельца процесса. После исправления повтори исходный случай, затем вернись к наблюдению реальной работы.
