# Ветка Bitrix24

Читай для технической работы с Bitrix24. Это повторяемая инструкция без домена, ключа, ID пользователя и настроек конкретной лаборатории.

## Установить фактическую среду

Различай облако и коробку, действующее подключение, аккаунт/пользователя, доступные инструменты и функцию CRM. Наличие полного каталога MCP не означает право записи, доступность функции на тарифе или разрешение задачи. Сохранённая конфигурация не доказывает, что инструмент загрузился в текущем чате.

Если в проекте доступны `bitrix24-vibecode`, `bitrix24-rest-api` или `bitrix24-mcp-server`, прочитай подходящий SKILL.md и используй его точные контракты в пределах проекта. Не копируй лабораторный профиль в новый клиентский проект. При отсутствии этих скиллов работай по текущей официальной документации и фактическим схемам доступного транспорта.

Сохраняй уже работающие MCP и хранилище доступа. Документационный MCP помогает найти метод; выполнение операций требует своего разрешённого инструмента. Не подключай новый сервер и не меняй глобальные настройки только потому, что внешний пример использует другой транспорт.

## Проверить контракт и настроить

1. Прочитай нужную текущую схему/метаданные. Для Vibe Entity API используй объявленные инструменты обнаружения и полей; для native REST — точную страницу метода и схему вызывающего инструмента.
2. Различай сущность, её тип, запись, категорию/воронку, стадию, поле и пользователя. Получи настоящие ID и перечисления этого портала. Не смешивай Vibe camelCase и форматы разных native REST API.
3. Для минимального изменения сохрани текущее состояние, цель и ожидаемые значения. Настройка новой сущности или карточки не разрешает удаление существующих полей/данных.
4. Выполни разрешённую операцию и перечитай значения/связи. Пользовательское поле или неподходящий ключ может не дать ожидаемого результата даже при успешном ответе.
5. Проверь затронутый рабочий случай, роль и существенное исключение. Для робота/процесса отдельно установи, что он действительно включён и сработал нужное событие с нужным результатом.

Перед изменением раскладки выясни, заменяет ли метод целиком её содержимое, как выбираются общая/персональная раскладки и пользователь. Прочитай исходное состояние и сохрани нужные части. Для пользовательских перечислений проверь требуемый формат списка и перечитай сохранённые варианты. Это проверяемые контракты конкретного метода, не универсальные формы параметров.

Коробочный PHP/D7-код и /local/ не являются способом настройки облачного портала. Ошибка прав не даёт основания отключать проверки доступа. Возможности тарифов, квоты и цены проверяй по текущему региону, не по кэшированному community-skill.

## Диагностика и возврат

Различай отсутствие инструмента в чате, неподдерживаемый метод, неподходящий транспорт/авторизацию, тариф, права, неверные параметры и временный сбой. Для отказа OAuth проверь действующий механизм обновления; не обещай auto-refresh, которого нет. Не извлекай токены в ответ и не запрашивай их повторно, если уже есть пригодное защищённое подключение.

При неясном исходе записи сначала проверь состояние. Повторы, batch и workflow со множеством эффектов требуют понимания конкретного поведения и разрешённого объёма. Отсутствие метода в discovery не доказывает отсутствие функции: сверяй официальную документацию и доступные способы вызова, не изобретая API.

После исправления вернись к исходному CRM-сценарию и наблюдению применения. Если ограничение платформы требует другого порядка работы, верни конкретный вопрос владельцу процесса. Если нужен собственный компонент — передай его в инженерный цикл, затем проверь путь с CRM.
