## Подтверждённые проблемы и ограничения

### 1. Переустановка может вернуть прежние модели

`scripts/install.py:370-374` копирует канонические TOML поверх установленных с резервным копированием. Поэтому нынешний источник установки отменит уже сделанный переход трёх ролей на Astra.

Просто скопировать новые TOML в Git недостаточно: `scripts/claude_agents_sync.py:35-36,129-134` знает только Terra/Sol и high/xhigh/max. Read-only вызов с актуальным worker воспроизвёл отказ для Astra, а отдельно — для Low. Нужна согласованная политика моделей для обоих хостов, без предположения, что уровни разных моделей эквивалентны.

### 2. Бюджеты делегирования относятся к разным единицам работы

Глобальные инструкции задают семь новых субагентов на пользовательский запрос; Task Delivery задаёт восемь на run (`graph.json:9,36`, `references/profiles-and-agents.md:31`). Разбиение задачи на несколько runs (`SKILL.md:201`) не обнуляет внешний счётчик. Глобальная инструкция уже требует после семи продолжать основным агентом, поэтому объявлять всю задачу заблокированной только по этой причине неверно.

Пожелание пользователя: убрать произвольный общий счётчик из логики остановки задачи. Предлагается сохранить ограничение одновременной нагрузки, независимость областей и остановку повторов без нового результата. Число запусков за долгую задачу использовать как сигнал расхода, а не бизнес-блокер. Ограничения платформы навык отменить не может: при их достижении продолжать доступную работу основным агентом; обязательную независимую проверку честно оставлять неподтверждённой до её выполнения.

### 3. Результат работы и состояние отключённого контроллера расходятся

В RESERCH run `39ffc3a5f0940b35` текущего Task Delivery 3.8.0 `state.json:12-25,56` содержит degraded/running, хотя manual closure фиксирует принятые слайсы и проверки. Это затрудняет продолжение и чтение статуса.

Предложение: единая сводка, отдельно показывающая принятую реализацию и состояние проверки графа, со ссылками на точные ручные квитанции. Не превращать degraded в verified автоматически и не закрывать старые runs задним числом без отдельного решения.

### 4. Выигрыш от замены исследователей пока не измерен

Подтверждено использование Terra High, но нет сопоставимого замера, что именно она расходует больше Astra при одинаковой задаче и качестве. Не следует просто перевести всех на тяжёлую модель или снижать все уровни рассуждения. Сначала сравнить модели/уровни на нескольких одинаковых ограниченных вопросах и измерить полезность результата, время, токены при наличии надёжного счётчика и повторное чтение основным агентом.

## Актуальные внешние рекомендации и применимость

- [OpenAI: GPT-6 Astra](https://developers.openai.com/api/docs/guides/latest-model#prompting-best-practices): модель чувствительна к неоднозначным инструкциям навыков; важны ясные условия продолжения, делегирования и достаточного тестирования. Отсюда кандидат на проверку: фраза о «новом решении» для CI/миграций в `task-delivery/SKILL.md:213` не должна провоцировать повторный запрос уже данного разрешения. Это гипотеза поведения, не доказанный сбой Astra.
- [Codex: experimental context management](https://learn.chatgpt.com/docs/models#experimental-context-management): заметки и поиск истории помогают продолжению между окнами. Сохранять durable plan/checkpoint как проверяемое состояние задачи; не заменять их памятью модели. Текущий граф уже не требует физического compact.
- [Codex: skills](https://learn.chatgpt.com/docs/build-skills): большой каталог может сокращаться. В начальном каталоге этой сессии PS/TD отсутствовали при наличии файлов; переполнение — вероятная, но непроверенная причина. Проверить явный вызов и обнаружение в новой задаче, прежде чем отключать или переименовывать другие навыки.
- [OpenAI: workflow evaluation](https://developers.openai.com/cookbook/examples/partners/macro_evals_for_agentic_systems/macro_evals_for_agentic_systems#1-why-macro-evals): оценивать путь выполнения, делегирование и проверки, а не только финальный ответ. Собственный `skills/agent-graph-builder/references/evaluation.md:45-69` уже требует такого сравнения: нужно выполнить существующий контракт под Astra, а не создавать ещё один процесс.

## Предлагаемый порядок следующей работы

1. **Воспроизводимая конфигурация.** Закрепить текущие роли в Git вместе с явной совместимостью Claude. Проверка: установка/повторная установка в временные homes сохраняет модели; проекция и общий gate проходят.
2. **Адаптивное делегирование.** Согласовать глобальные правила и граф: 0–2 субагента одновременно по умолчанию, отдельные области, без общего числа запусков как причины остановить задачу. Разделить «работать этапами» и «обязательно создавать worker на этап». Сохранить независимое ревью существенного риска. Проверка: длинная задача с более чем семью полезными этапами не останавливается из-за счётчика и не обходит ограничения хоста.
3. **Небольшой сравнительный прогон.** Шесть сценариев: простой фикс, Project Start maintenance, длинные слайсы, продолжение после смены окна, уже разрешённая CI-правка, отказ контроллера. Сравнить текущий профиль с кандидатом; исследовательские модели менять по результату. Фиксировать реальные дефекты, лишние вопросы, повторы тестов, запуски, время и доступные метрики расхода.
4. **Только доказанные улучшения.** Уточнить неоднозначные правила и отображение degraded/manual результата по итогам прогонов. Старые квитанции, scope и требования проверки не ослаблять.

Следующая реализация требует согласования этого плана; текущий запрос был на исследование и обсуждение. Новые модельные прогоны не выполнены, обещания процента экономии или роста качества отсутствуют.
