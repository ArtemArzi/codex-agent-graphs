# Экономное делегирование и отложенная инженерная база

Дата: 2026-09-14. Статус: предложение; активные правила не изменены.

## Запрос пользователя

Сохранить идею общей инженерной базы для всех проектов. Сейчас разобрать чрезмерное делегирование: основной агент уже знает контекст и может выполнить небольшую работу, но передаёт её новому агенту, который заново изучает задачу. Упростить выбор исполнителя, сохранив необходимые проверки и безопасность.

## Что показала текущая проверка

Канонический источник — этот репозиторий. Просмотрены policies/model-routing.toml, policies/orchestration.md, policies/large-codebase-discovery.md, прежний docs/tasks/TD-ADAPTIVE-DELEGATION/PLAN.md и установленный agent-graph-builder/references/efficiency-contract.md. Соответствующие спорные фразы присутствуют также в установленном глобальном `AGENTS.md` Codex. Полная синхронность всех установок этим проходом не устанавливалась.

- Efficiency contract уже требует начинать предметную работу самостоятельно и учитывать стоимость запуска, передачи контекста и интеграции.
- policies/model-routing.toml:10 предписывает отдавать auxiliary agents сбор информации, реализацию и подготовку документов без явного условия полезности. Строка 13 задаёт дополнительные focused reviews по умолчанию.
- policies/orchestration.md:5 явно разрешает непосредственную работу только для trivial или тесно связанных integration steps. Это можно прочитать как ограничение права главного агента выполнять обычную реализацию.
- policies/large-codebase-discovery.md:5–6 после входа в режим большой разведки связывает появление двух вопросов с остановкой root-сканирования и делегированием. Два вопроса сами по себе ещё не означают, что передачу контекста можно окупить.
- Исторический план TD-ADAPTIVE-DELEGATION описывает старую optional/risk-triggered review политику. Текущий model-routing имеет приоритет; исторический COMPLETE не является действующим исключением из независимой приёмки.

Вывод: это неоднозначность и конкуренция формулировок, способная провоцировать лишние запуски. Частота такого поведения и фактический расход токенов пока не измерены; по одному тексту нельзя доказать единственную причину всех лишних запусков.

## Предлагаемое главное правило

Основной агент может сам читать, исследовать, реализовывать, тестировать и документировать задачу. Наличие роли исполнителя не запрещает непосредственную работу. Если нужный контекст уже собран и следующий шаг локален, продолжать самостоятельно.

Делегирование — выбор по ожидаемой пользе, а не обязательный этап. Учитывать стоимость постановки, повторного чтения, ожидания, проверки и интеграции. Более дешёвая модель сама по себе не доказывает экономию всей задачи.

## Практическая граница

| Ситуация | Предпочтительное действие |
| --- | --- |
| Прочитать короткий файл, найти символ, уточнить известный контракт | Главный агент делает сам |
| Небольшая связанная правка и её тест в уже понятном коде | Главный агент делает сам, независимо от числа файлов |
| Следующий шаг требует результата предыдущего и почти всего того же контекста | Продолжить одной последовательной работой |
| Нужно независимо исследовать неизвестный, содержательный участок, пока root решает другую полезную часть | Делегировать ограниченный вопрос, если затраты оправданы |
| Обособленная реализация со стабильным интерфейсом и существенным объёмом | Можно делегировать; наличие интерфейса не обязывает это делать |
| Обязательная независимая приёмка существенной задачи | Отдельный проверяющий по действующей политике |

Это примеры, не числовые пороги. Не определять сложность только числом файлов, строк или пунктов плана. Маленькая правка доступа или финансового правила может быть высокорисковой.

## Передача контекста без повторного полного исследования

- Передавать конкретный вопрос, известные факты с точными ссылками, ограничения и оставшуюся неизвестность.
- Не просить заново исследовать весь проект, если задача уже ограничена известным путём.
- Исполнитель проверяет необходимый исходный контекст и решающие факты; экономия не отменяет чтение применимых AGENTS.md, обязательных skill instructions и источников.
- Главный агент проверяет решающие утверждения и места интеграции, а не повторяет всю разведку.
- Не отдавать микрошаг в отдельную роль, если постановка и принятие результата сопоставимы с непосредственным выполнением.
- Не создавать расчёт бюджета или отдельный файл оправдания для каждого запуска. Достаточно короткого объяснения полезности в назначении.

## Что изменить при внедрении

1. В policies/model-routing.toml заменить безусловное распределение предметной работы разрешением root выполнять её целиком; auxiliary agents подключать условно, по пользе.
2. Там же заменить focused reviews «по умолчанию» на дополнительные независимые проверки конкретного риска, который не покрывается основным проверяющим в его назначенной области. Не создавать отдельного проверяющего для каждого вопроса.
3. В policies/orchestration.md убрать впечатление, что root разрешены лишь trivial/integration steps. Сохранить запрет дублирования, ограничение параллельных писателей и leaf-only работу.
4. В large-codebase-discovery.md сохранить делегирование действительно широкой неизвестной работы, но считать два вопроса поводом оценить разделение, не автоматическим условием запуска. Это предложение изменить текущий триггер, а не действующее исключение из него.
5. Сверить затронутые инструкции Task Delivery, Project Start и efficiency contract; устранять только противоречия, не размножать полный текст политики по скиллам. Использовать существующие ссылки и владельцев правил.
6. Проверить установщик и применить согласованные изменения через канонический источник с защитой от drift, резервными копиями и проверкой нужных установок. Не редактировать сгенерированные AGENTS.md вручную и не менять графы, модели или схемы receipts ради изменения словесного выбора исполнителя.

## Независимая приёмка — отдельная граница

В предлагаемом первом изменении сохраняются fresh whole-plan и другой whole-result acceptor для существенной задачи. Root может сам выполнить всю реализацию между ними. Это две границы на задачу, не на каждый файл, поиск, шаг или скилл. Плановая работа закрывается приёмкой плана по действующей политике.

Убрать эти две проверки для класса небольших задач — отдельное изменение пользовательской гарантии, которое нельзя скрыть под экономией исполнителей. В этом предложении оно не принято. Не дробить существенную задачу на «простые» шаги для обхода приёмки. Не использовать это предложение, чтобы задним числом считать действующие обязательные проверки необязательными.

## Как проверить, что поведение улучшилось

- Короткое чтение/поиск: нет нового explorer/worker и нового цикла приёмки для внутреннего шага.
- Связанная реализация в известном контексте: root может выполнить её без worker; необходимые проверки всей задачи сохранены.
- Два коротких вопроса по известному коду: не приводят автоматически к двум исследователям после принятия нового триггера.
- Действительно широкая неизвестная задача: полезное независимое исследование остаётся доступным, без повторяющихся назначений.
- Чувствительная финансовая/авторизационная правка: малая длина diff не отменяет приёмку и проверки риска.
- План и результат существенной задачи: независимые проверяющие разные; дополнительные focused agents не появляются автоматически.

Сначала проверить исходные формулировки и установку, затем провести одинаковые поведенческие сценарии до/после в свежих корневых сессиях. Сравнивать ненужные запуски, повторные чтения, время, фактические доступные token/cost данные и качество результата. Меньшее число агентов — наблюдение, но не доказательство экономии или качества. Не строить отдельную систему телеметрии ради этой правки.

## Отложено: общая инженерная база

Назначение: общий справочник выбора решений для всех проектов, а не дополнительный обязательный workflow и не документ только для RESERCH.

Начальное ядро: границы модулей, обработка ошибок, транзакции, идемпотентность, авторизация и тестирование. Для паттерна: задача, условия применения/неприменения, небольшой пример, проверка правильности, первичный источник.

Разделение ответственности: общая база объясняет выбор; скиллы указывают, когда обратиться; документация проекта фиксирует выбранное решение и ограничения. Перед созданием сверить существующие скиллы и ARCHITECTURE_PLAYBOOK.md, использовать ссылки вместо дублирования. Не делать чтение всего справочника обязательным для каждого плана. Сначала разобраться с экономным исполнением, затем вернуться к базе; отдельный аудит RESERCH этим не заменяется.

## Состояние этого прохода
