# Delivery plan

Accepted: preserve the current cache file format and caller return type. Network is not available in offline mode.

Current next step: step 1, inspect the real caller contract and settle stale-cache indication without changing the accepted invariants. Planning is complete; implementation has not started.

## Основание и границы

Источник: README.md, AGENTS.md и app.py этой папки. В app.py есть только write_cache(path, payload): JSON записывается через Path.write_text(json.dumps(payload)). Чтение, сетевой клиент, вызовы и тесты не представлены. Не приписываем им существующий интерфейс или тип результата.

Задача: добавить чтение существующего кэша без сети в offline-режиме и понятное указание устаревания. Формат JSON и тип результата для вызывающей стороны сохраняются. Код app.py в рамках планирования не изменяется. Новый формат, обязательная миграция файлов, фоновое обновление и обращение к сети из offline-ветки не входят в план.

Путь данных: вызывающая сторона -> выбор offline -> безопасное чтение локального файла -> разбор JSON -> прежний тип результата. Признак устаревания передаётся отдельно от payload способом, совместимым с фактическими вызовами.

Неизвестно: текущий интерфейс чтения и тип результата у реального клиента, место выбора offline, доверенная область путей, допустимый размер кэша, порог устаревания и ожидаемое поведение при отсутствии/повреждении файла. Это пробелы исходных данных, а не принятые решения.

## Последовательность по рабочим сеансам

Все шаги пока запланированы. Зависимости: 1 -> 2 -> 3. Параллельная реализация не даёт пользы: контракт чтения определяет код и проверки. Ветки, PR и CI здесь не проверялись и не обязательны; использовать существующий процесс целевого проекта.

### 1. Уточнить совместимый контракт чтения

Контекст для нового сеанса: владелец плана docs/PLAN.md; принятые ограничения в начале файла. app.py содержит лишь write_cache; выдумывать потребителей нельзя.

Работа: найти реальные вызовы, механизм offline и проверки целевого клиента. Зафиксировать точный тип результата, ошибки cache-miss/corrupt/unreadable и способ сообщать stale без обёртки вокруг payload. Предложение для обсуждения по фактическому коду: отдельный существующий канал статуса или callback; возраст по mtime файла без изменения JSON. mtime показывает возраст записи файла, а не гарантированную свежесть исходных данных. Порог свежести брать из принятой политики, пока он неизвестен. Отсутствие кэша не должно вести к сетевому fallback.

Проверка: таблица «сценарий -> результат/ошибка -> статус», подтверждённая вызовами. Проверить, что обычный JSON из write_cache читается без преобразования формата и что stale-статус не меняет прежний тип. Если реальных вызовов нет, сохранить этот пробел и не выдавать предложенный контракт за подтверждённый.

Выход: конкретный совместимый контракт и перечень проверок записаны здесь. При противоречии принятому типу/формату остановить зависимую реализацию и уточнить именно конфликт. Откат: до реализации только вернуть собственные изменения контракта в плане; пользовательские решения сохранять.

### 2. Реализовать ограниченную offline-ветку

Контекст: выполнять только после шага 1; формат write_cache, тип результата и запрет сети неизменны. Потребители, политика stale и ошибки должны быть перечислены в результатах шага 1.

Работа: в существующем модуле добавить чтение по согласованному интерфейсу, обработать отсутствие, ошибку доступа, некорректную кодировку/JSON и устаревание. Не возвращать повреждённые данные как успех. Проверить границы доверия пути; если путь приходит извне, ограничить его принятой областью кэша, включая поведение symlink. Не добавлять произвольные ограничения размера или удаления без основания; при необходимости согласовать их в контракте. Сохранить файлы при ошибке чтения. Сетевой код должен быть недостижим в offline-ветке, включая обработку cache-miss и stale.

Проверка: локальные временные файлы для valid/missing/corrupt/unreadable/fresh/stale; часы и сеть подменены. Сеть-заглушка падает при любом обращении. Сравнить тип результата с контрактом шага 1 и проверить исходный файл до/после чтения. Проверку прав выполнять воспроизводимым способом, не полагаться только на chmod под привилегированным пользователем.

Выход: сценарии проходят, новых сетевых вызовов и изменения формата нет. Откат: отключить или вернуть только новую ветку; существующий кэш не менять и не удалять.

### 3. Проверить весь пользовательский путь и завершить передачу

Контекст: после шага 2, проверяется фактический вызов клиента, а не только функция чтения. Синтетические проверки отдельно от результата на реальном клиенте.

Работа: пройти online-запись существующим write_cache -> offline-чтение при заблокированной сети; повторить с устаревшим и повреждённым файлом. Проверить отображение stale в согласованном канале и сохранение типа результата. Запустить существующие релевантные проверки online-пути, если они есть. Обновить существующую документацию пользователя: включение offline, stale, cache-miss и восстановление повреждённого кэша.

Выход: подтверждены формат и тип, отсутствие сети во всех offline-сценариях, stale-статус виден вызывающей стороне; фактические команды и результаты записаны в этом плане. Непроверенные сценарии обозначены. Откат: вернуть только реализацию и её документацию, кэш оставить. Завершать по применимому независимому review проекта; сейчас независимая проверка не проводилась, агенты запрещены условиями упражнения.
