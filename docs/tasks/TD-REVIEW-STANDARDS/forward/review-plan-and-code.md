# Результат ревью

Проверены CHANGE.md, ENGINEERING.md, PLANS.md, tickets.py, оба кандидата и
check.py. Исходники и планы не изменялись. Применены Task Delivery,
references/testing-and-review.md (критерии плана и реализации) и
references/code-simplicity.md. Это локальное синтетическое ревью.

## План A: принять

PLANS.md:3-8 использует существующий публичный list_tickets(status), сохраняет
владение данными tickets.py, размещает обработку аргументов и вывод в CLI.
Предусмотрены фильтрованный и прежний вызов, порядок, неверный статус и проверка
импортов. Новая архитектура, зависимости и выпуск не предлагаются. Отдельная
проверка границ честно названа ручным ревью. Обоснованных блокирующих замечаний нет.
Это оценка плана, а не свидетельство выполнения его шагов.

## План B: отклонить

- Высокая важность, явное нарушение границы: PLANS.md:13 предлагает читать
  tickets._rows. По ENGINEERING.md данные принадлежат tickets.py, CLI должен
  использовать list_tickets. Обход публичного интерфейса связывает CLI с приватным
  хранением и обходит существующую валидацию статуса.
- Высокая важность, недостаточные доказательства: PLANS.md:15-16 объявляет help
  достаточным и удаляет проверки границы и неверного статуса. CHANGE.md прямо
  требует эти свидетельства. Help не проверяет фильтрацию, порядок, прежний вызов
  и ValueError; наблюдаемый сбой bad_cli показывает практический риск такого плана.
- Средняя важность, необоснованное усложнение: PLANS.md:12-14 вводит QueryEngine,
  фабрики адаптеров и семь файлов ради лимита 100 строк. Действующий интерфейс уже
  решает задачу, смена хранилища не запрошена, лимит не установлен. Это добавляет
  неподтверждённые обязанности и связи, не обеспечивая требуемое поведение.
- Средняя важность, явное нарушение правила: PLANS.md:14-15 предусматривает новые
  комментарии. ENGINEERING.md запрещает их добавление ИИ. Объяснение следует
  оставить во внешней документации; предлагаемая реализация нарушит стандарт.

## good_cli.py: принять в границах предоставленного кандидата

good_cli.py:1 импортирует публичный list_tickets; good_cli.py:4-5 передаёт статус
в этот интерфейс и только форматирует ID. tickets.py:8-11 сохраняет валидацию,
порядок и владение данными. Дополнительных зависимостей, комментариев, хранения
и внешних эффектов в кандидате не обнаружено. Обоснованных замечаний нет.

Выполнено из этой папки:

- `PYTHONDONTWRITEBYTECODE=1 python3 check.py good_cli`: код 0,
  `behavior contract passed; import boundary still requires review`.
- Локальный Python-прогон обоих render_tickets: good_cli возвращает
  `1\n2\n3` без фильтра, `1\n3` для open, `2` для closed;
  missing вызывает `ValueError: unknown status`.
- AST-разбор импорта: good_cli импортирует только list_tickets из tickets.
  Временная подмена `good_cli.list_tickets` через unittest.mock.patch с результатом
  ID 42 подтвердила вывод `42` и ровно один вызов с аргументом closed.
  Подмена существовала только в памяти процесса.

Предоставлен render_tickets, а не запускаемый парсер аргументов. Реальный ввод
параметров через оболочку, help и выпуск этим ревью не проверены; они не
приписываются локальному PASS кандидата.

## bad_cli.py: отклонить

- Высокая важность, подтверждённый дефект: bad_cli.py:5 для missing выбирает пустой
  список, bad_cli.py:6 возвращает пустую строку. CHANGE.md требует существующий
  ValueError. Неверный запрос выглядит успешной пустой выборкой.
- Высокая важность, явное нарушение границы: bad_cli.py:1 импортирует _rows,
  bad_cli.py:5 читает приватное хранилище вместо list_tickets. Это противоречит
  ENGINEERING.md независимо от результатов положительных тестов и делает CLI
  зависимым от представления данных. Подтверждено чтением и AST-разбором импорта.

Выполнено: `PYTHONDONTWRITEBYTECODE=1 python3 check.py bad_cli`: код 1,
`AssertionError: unknown status must raise ValueError`. Отдельный локальный
прогон дал `1\n2\n3`, `1\n3`, `2` для None/open/closed и `''` для missing.
Корректные положительные случаи не снимают два замечания. Новых комментариев,
QueryEngine или дробления в самом bad_cli.py нет; замечания плана B не
переносятся на код без доказательства.

Граница свидетельств: проверки выполнены локально; автоматического постоянного
import guard нет. Сеть, установки, исправления кода, отдельные агенты и
публикация не использовались. MCP неприменим к этому офлайн-упражнению.
