# Основание проекта

## Цель
Сохранять заявки и показывать их оператору через существующее локальное решение.
Будущее улучшение: уведомлять оператора после создания заявки. Код в этом
проходе не меняется. Принятый стек и совместимость принадлежат DECISIONS.md.

## Проверенные факты и профиль
OPERATIONS.md описывает локальный CLI, Python standard library, SQLite и одного
оператора. В исходниках доступны только функции, executable CLI/парсер аргументов
в fixture отсутствует. Нельзя выдумывать команду запуска CLI.
Python проверочной среды: 3.12.3; поддерживаемый диапазон проекта не закреплён.
Код не содержит внешних интеграций, credentials или worker. Нет подтверждения
backup/restore. Нагрузка, объём данных, бюджет, срок, допустимый простой/потеря,
чувствительность текста, права и будущая конкуренция неизвестны. Это влияет на
будущую реализацию, но не мешает сохранять текущее основание.

## Карта исполнения и владение
| Изменение/поток | Interface и implementation | Данные/потребитель | Проверка/владелец договора |
| --- | --- | --- | --- |
| Создание | tickets.py:create_ticket(connection, text) | Таблица tickets; соединение передаёт caller, функция выполняет commit | tests/test_tickets.py; OPERATIONS.md, DECISIONS.md |
| Просмотр | tickets.py:list_tickets(connection) | Таблица tickets; SELECT ORDER BY id; callers в fixture только тесты | tests/test_tickets.py; OPERATIONS.md |
| Уведомление | Ещё не реализовано | Будущий внешний канал неизвестен | Предложение ниже; QUALITY.md, PLAN.md |

CREATE TABLE IF NOT EXISTS выполняют обе функции. create_ticket проверяет strip(),
но сохраняет исходный текст; пустой текст вызывает ValueError('empty ticket').
Параметризованный INSERT и commit предшествуют возврату cursor.lastrowid.
list_tickets возвращает список пар. Ошибки SQLite не скрываются. Текущий create
не имеет ключа повторного запроса; нельзя обещать дедупликацию заявок.

## Сравнение сохранения и изменения стека
1. Сохранить stdlib + SQLite и функции: соответствует принятому local/single-
operator договору, нет миграции или новых сервисов. Ограничение: будущие
параллельные записи и эксплуатация потребуют отдельной проверки.
2. Перенести в web/service с серверной БД: могло бы дать удалённый многопользовательский
доступ, но такого требования нет; добавляет deployment, права и миграцию.
Рекомендация: сохранить вариант 1. Это оценка текущего выбора, не восстановленная
история утраченного сравнения. Микросервисы, брокер и framework не обоснованы.

## Предложение уведомлений, ещё не принято
Сценарии потребителя:
- Оператор создаёт 'Help with login', получает сохранённый ID, затем узнаёт о
  новом обращении через выбранный канал. ID остаётся прежним числовым результатом.
- Пустой текст отклоняется; ни заявки, ни уведомления быть не должно.
- Канал недоступен после сохранения: предлагаем сохранить заявку, показать
  недоставленное уведомление и дать повторить его без повторного создания заявки.
- Процесс завершился между сохранением и отправкой: необходимый способ
  восстановления зависит от принятой допустимости потери уведомления.

Вариант A: отправить сразу после commit в том же процессе. Минимум изменений,
но сбой между commit и отправкой теряет попытку; повтор create создаёт дубликат
заявки. Подходит лишь при явном согласии на best effort, которого пока нет.
Вариант B (условно рекомендуемый при требовании восстановления): вместе с заявкой
сохранить намерение отправки в SQLite, отдельным явным проходом доставлять
ожидающие уведомления. Дополнительная таблица/обработка требуют миграции и
проверки рестарта, но не нового брокера или сервера. До ответа владельца это
предложение, не обязательное принятое усложнение.

Минимальный предлагаемый договор: create сохраняет старый return ID; логика
уведомления не меняет смысл успеха создания. Владелец tickets остаётся tickets.py;
возможное сохранённое намерение принадлежит логике уведомления, связано с ticket_id.
Отправитель получает ticket_id и разрешённый payload; возвращает подтверждение
либо сообщает ошибку. Канальный adapter и точные status/error схемы выбрать
после канала; общий plugin framework заранее не нужен. Регистрация зависимостей
должна происходить у будущего реального caller, которого сейчас нет в fixture.

Для B одно намерение на ticket_id и тип уведомления; pending/sent/failed только
предложенные состояния. Обычный повтор отправки не создаёт заявку. Падение после
приёма провайдером до отметки sent может дать повтор: exactly-once не обещать,
после выбора провайдера проверить ключи дедупликации и reconciliation. Timeout,
число повторов, задержки и время ручного вмешательства ещё не согласованы.

## Эксплуатация и границы проверки
Никаких production/внешних действий в этом проходе. Секреты будущего канала
хранить вне документации; состав текста для отправки и доступ должны быть
согласованы. Наблюдение будущей доставки должно различать сохранённую заявку,
ожидающую отправку и подтверждение провайдера; избегать текста заявки в логе
по умолчанию. Backup, миграцию и восстановление репетировать на копии перед
изменением хранилища. Владелец поддержки пока неизвестен.

Основание: локальные OPERATIONS, DECISIONS, tickets.py и tests/test_tickets.py;
кандидат Project Start architecture-playbook и architecture-from-usage прочитаны
2026-10-15. Внешние источники не открывались: сеть исключена условиями прогона.
Нет новых provider/API рекомендаций. Предложение интеграции требует актуального
primary-source исследования выбранного канала до реализации; это явный пробел,
не completed research. Проверки и последовательность: QUALITY.md и PLAN.md.
