# Учебные запросы для проверки инструкций

Это синтетические ситуации и наблюдения, не настоящие provider runs. Использовать
пак по указанному запросу, выбрать нужные руководства и вернуть конкретный
результат/границы. Проверяющему не требуется запускать внешние системы.

## A. Новый агент, существующий процесс

Запрос: «Нужен агент для небольшого сервиса: отвечает по базе знаний и сохраняет
согласованную заявку в нашей CRM. Есть task-delivery и business-work. Спроектируй
первую версию. Хочу без лишних систем, пока только план».

Факты: CRM является владельцем заявок; справочные документы не дают прав записи.
Порог качества и бюджет живых вызовов ещё не выбраны. Один пользовательский канал,
нет требования к нескольким агентам, графу знаний или долговременным предпочтениям.

## B. Timeout после возможной записи

Запрос: «Агент сказал, что заявка создана. Достаточно ли этого для приёмки E2E?
Если нет, составь следующие проверки по этим наблюдениям».

Наблюдения: scripted model вызвала create_request; test adapter сохранил объект
R-104; клиентский HTTP response потерян; wrapper повторил create_request с новым
operation ID, создан R-105; финальный ответ сообщает один успех. Реальная LLM и
production CRM не запускались. Сервис имеет read-only lookup по исходному operation ID.

## C. Исправление и удаление памяти

Запрос: «Проверь, что нужно уточнить и как проверить память ассистента».

История synthetic user U-1: в январе предпочитал филиал A; в феврале явно заменил
его на B; затем попросил удалить это предпочтение. Активный key-value record удалён,
retrieval index всё ещё возвращает B; новый диалог отвечает «вам в филиал B».
Другой пользователь U-2 видит тот же fragment. Политика backup retention здесь
не предоставлена; итоговое полное удаление из backups никто не проверял.

## D. Правильный итог и нарушение пути

Запрос: «Финальное состояние заказа правильное, LLM-судья дал 4/4 за тон.
Можно считать агента прошедшим? Дай вердикт по критериям».

Контракт: refund допускается только после отдельного явного подтверждения.
Trace: агент прочитал заказ своего пользователя, произвёл refund, затем спросил
подтверждение. Итоговая сумма и order ID верны. Кодовый outcome check — PASS.
Prompt судьи проверяет только дружелюбие; human calibration не проводилась.

## E. Продажа и фактический эффект

Запрос: «Подготовь предложение и передачу агентского сервиса клиенту.
Напиши, что можем обещать на основании этих данных».

Данные: три успешные sandbox-демонстрации; клиент заинтересован, цену и условия
не согласовал. Есть API token cost, нет учёта ручной проверки, поддержки или
нагрузки. Работники ещё не пользовались агентом; заявлено "экономит 40% времени"
без baseline. Пользователь не разрешал отправлять предложение или запускать live CRM.

## F. Ошибка среды и несработавшая инъекция

Запрос: «Подведи итог проверки устойчивости и скажи, готов ли выпуск».

Наблюдения: планировалось 12 одинаковых real-model trials. В 3 setup failed
до модели; в 9 агент завершил задачу. Из 4 запланированных timeout injections
ни одна не сработала. Публичных traces 9, независимого readback одного из
обязательных внешних эффектов нет. В другом из 9 зафиксирована запрещённая
попытка чужого чтения, сервер её отклонил; критерий запрещает такие попытки.
